# Posta Multi 235M — Run 001

**Canonical plan, updated 2026-11-21.** This supersedes any earlier
compact-first proposal in README.md. The owner explicitly chose the
full **235,179,777-parameter** architecture.

Run ID: `posta-multi-235m-run-001`. Architecture `Config()` plus
`text_pooling='mean'`: 12-layer 768-wide text tower, 12-layer 768-wide
image tower, temporal audio/video stack and fusion transformer.
**All new Run 001 weights are randomly initialized.** Previous
`mixed-v2`, `retrieval-v1`, `image-v1`, `audio-v7` and `text-v8` and
`retrieval-adam-v9` weights are historical experiments, never a
pretraining starting point.

## Immediate execution order

1. **Read-only preflight**: `run001_text.py --preflight` uses local corpus
   manifest, tokenizer SHA-256/metadata, vocabulary IDs and CUDA presence.
   It reports `allowed_to_train: false` if privacy or data rights are
   unreviewed. The cron writes
   `/mnt/hdd_ubuntu/posta-pmr/posta-multi-235m-run-001-preflight.json`.
2. **Real-GPU synthetic smoke**: `run001_smoke.py` initializes the complete
   multimodal model at random, freezes non-text parameters, enables
   activation checkpointing and attempts **one actual FP16 masked-LM
   forward/backward + CPU-FP32 AdamW update** on synthetic IDs under 45% of
   CUDA allocator memory. Cron runs it once only after previous GPU
   evaluations end. JSON-only output is
   `/mnt/hdd_ubuntu/posta-pmr/posta-multi-235m-run-001-smoke.json`.
   A failure does *not* automatically re-run or lower safety limits.
3. **Multilingual tokenizer**: train a **new** stable byte-level BPE with
   enough properly cleared Russian, English and other target-language
   documents; keep special IDs 0/1/2/3, record source revisions and SHA,
   and verify round-trips and token-length distributions. The old
   RU/EN tokenizer is a pilot; its 65k slots alone do not imply language
   understanding. Do not change tokenizer mid-run.
4. **Stage 1: text pretraining from scratch**, once the data passes all
   required checks, using `run001_text.py`. It uses balanced hash-selected
   text across text/retrieval/OCR/image/meme/video/speech record types,
   dynamic 15% token masking with bounded logits, two microbatches per
   AdamW step (configurable), CPU-master optimizer, activation
   recomputation, periodic held-out validation, atomic `last` and
   `best` checkpoints, exact provenance and RNG-based resume.
   The *initial* 2000-step default is only a pilot to calibrate memory,
   throughput and loss trends, **not** a complete 235M pretraining budget.
5. **Stage 2: query–post alignment** using audited multilingual
   query/relevant-document/explicit-negative examples, avoiding accidental
   false negatives and handling positive-only rows deliberately. Evaluate
   against lexical BM25, a random encoder, and previously published
   baselines on an independently labeled, much larger query set.
6. **Stage 3: image captions and OCR**, then memes, video frames/subtitles
   and speech/audio as separate cross-modal alignment curricula; retain
   common embeddings but score *sources* and *individual posts* separately.
   Maintain target search latency and precomputed top-100 caches in the
   existing Go backend, outside model weight training.

## Data growth: grounded source candidates

The current local screened candidate has only **74,302 records** and
**25,546,970 whitespace-delimited words**; it is *quarantined*. It is not
enough to establish broad cross-lingual, all-topic semantics with a 235M
model trained from scratch. Prioritize new training material as follows:

| Stage | Candidate | Purpose | Usage constraints / upstream |
|---|---|---|---|
| Text (EN) | [HuggingFaceFW/fineweb-edu](https://huggingface.co/datasets/HuggingFaceFW/fineweb-edu) | Large filtered English Common Crawl pretraining text | ODC-By 1.0; site/crawl terms and privacy still need review |
| Text (RU + others) | [epfml/FineWeb2-HQ](https://huggingface.co/datasets/epfml/FineWeb2-HQ) | Model-filtered quality subset, 20 languages including Russian | ODC-By 1.0 plus Common Crawl terms; quality filter relies on XLM-R embeddings, not trained Posta weights |
| Text (broader) | [HuggingFaceFW/fineweb-2](https://huggingface.co/datasets/HuggingFaceFW/fineweb-2) | Diversify further languages and domains beyond HQ | ODC-By 1.0; much larger/noisier, select small balanced shards |
| Retrieval | [hotchpotch/FineWeb2-IR](https://huggingface.co/datasets/hotchpotch/FineWeb2-IR) | Multilingual query-document synthetic relevance pairs (Russian ~2.78M listed) | Derived from FineWeb-Edu/FineWeb2-HQ; queries synthesized with external query-crafter model, inherits source terms |
| Evaluation | [MIRACL](https://huggingface.co/datasets/miracl/miracl) | External multilingual retrieval evaluation | Reserve held-out evaluation data; verify individual collection terms before usage |

Do **not** automatically download terabytes or treat an aggregate ODC-By
label as individual-document rights clearance. Start with source/version
inventory, narrow language-balanced samples, explicit source references,
license/terms, privacy scan, near-duplicate and benchmark-contamination
screening, content balance and reproducible train/validation partitions.
Select sampler sizes based on available disk, not data listing sizes.
Record SHA-256 for each downloaded shard. A larger corpus is necessary
but not a guarantee of quality. More steps and more relevant supervision
are essential.

## Hardware and feasibility

Local expected device: GTX 1060 **3 GiB**, shared with a desktop. Keep the
existing **45% PyTorch allocator fraction** for experiments unless explicitly
revised after measuring free VRAM. Offload the FP32 masters and Adam moments
to host RAM; preserve full 235M model weights in FP16 and recompute text
encoder activations. Probe before full execution. An OOM or CPU RAM shortage
means the budget needs to change, **not** that we should silently substitute
a smaller architecture.

Full 235M text training with this hardware may be extremely slow. An
initial pilot success says only that a GPU step is feasible. Report
updates/second, allocated MiB and measured held-out loss, not just
'checkpoint saved' or an arbitrary v-number.

## Checkpoint contract

- `Run 001` is one experiment; **step** is the optimizer update count.
- Stage 1 outputs (new directory only):
  `run001-text-last.pt` (full model, CPU optimizer, RNG, settings),
  `run001-text-best.pt` (best validation checkpoint).
- The checkpoint has its own format and fixed config, tokenizer,
  manifest/selected-data hashes, learning rate, batch settings and seed.
  Resuming refuses mismatched settings.
- No stage auto-promotes weights to Posta production. Passing 16 local
  queries is insufficient. Do not recycle the internal test set for
  hyperparameter tuning.

### Balanced checkpoint selection

The previous draft chose the best checkpoint from the first 16 globally
hash-sorted validation token windows. This could overrepresent one language
or modality. Run 001 now uses up to four unique, hash-ordered windows per
(kind, language) group from the validation partition. Every window is
evaluated with deterministic masking; best checkpoint is selected by the
macro-average MLM loss across groups. Per-group means, counts and the
exact selected-window fingerprint are recorded. The checkpoint format is
v2; it will refuse to resume with a changed validation selection.
This is internal model validation, not independent retrieval benchmarking.

### Run 001 full-length GPU feasibility gate

The initial one-step synthetic probe at 24 tokens is **not** a valid
estimate of 96-token training VRAM requirements. A second **one-shot**
probe uses the same 235M architecture, 45% PyTorch allocator cap,
FP16 text gradients and CPU-master AdamW, but with a 96-token sequence
and 8 masked targets. It starts only after a successful short probe,
does not touch real data and writes numeric results to
`posta-multi-235m-run-001-seq96-smoke.json`, `.log`, `.exit` on the HDD.
An OOM, timeout or skipped run must be reported, not treated as proof
that real-data training is feasible. The new test does not overwrite
historical Run 001 smoke results.



### Run 001 gradient safety

The CPU-master AdamW optimizer now supports **opt-in FP32 global gradient
norm clipping**, guarding against extreme updates from randomly initialized
235M text training. The legacy experiments retain their old default
(no clipping) and their checkpoint format compatibility. Run 001 and its
synthetic smoke use `max_grad_norm=1.0`. A step with no gradients or
nonfinite gradients is rejected; gradient norm and clip multiplier are
logged numerically. Resume checks the saved optimizer's clipping policy,
preventing accidental changes mid-run.



### Text split isolation before full Run 001 allocation

Run 001 now compares the selected text from ALL kinds and languages in
train and validation after NFKC normalization, casefolding and whitespace
collapsing. Even one shared text blocks training **before** the 235M model
is initialized. This reports only distinct collision counts and never
publishes the raw text. The check does not detect paraphrases, translations
or near-duplicates; the wider corpus audit remains necessary. Because the
training-data isolation contract changed, the text checkpoint format is
`posta-multi-235m-run001-text-v3`.
