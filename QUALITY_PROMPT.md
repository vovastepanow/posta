# Задача: качество подбора — в карточки попадает не то

Ты работаешь в PHP-проекте `/var/www/html/posta` (Posta: парсер собирает посты из Telegram, VK, Двача и др.,
локальная vision-модель оценивает каждый пост по теме пользователя, подходящие идут в карточки; пользователь
ставит лайк, дизлайк или жалуется «не по теме»).

Владелец: «качество подбора хромает». Речь **не** о количестве источников, а о том, что из найденного модель
пропускает в карточки.

## Что выяснено (2026-10-23, по истории оценок — перепроверять не нужно)

Данные: 610 оценённых карточек по мемным темам («Мемы и юмор», «мемы и приколы», «Абсурдный юмор») из
`history_items` (коллекции `liked`, `disliked`, `complaints`; у всех жалоб причина `match_error` = «не по теме»).
По другим темам данных почти нет — выводы сделаны на мемах, но причины общие.

**Сейчас: лайк 37%, дизлайк 31%, жалоба «не по теме» 30%.** Почти каждая третья карточка — промах модели.

1. **Модель додумывает.** Типичные `why_relevant` у жалоб с оценкой 85: «может подойти для мемов про уют»,
   «возможного контекста (например, мем про девушку с вином)», «может быть частью мема про голосовые помощники»,
   «необычного и немного смешного вида мышей». Это фото щенков, летучих мышей, аниме-девушки — не мемы.
   Карточки, где в `why_relevant` есть «может / возможн / если / вероятно / потенциальн / подойти для»:
   **56 штук, 0% лайков, 85% жалоб.**
2. **Шкала оценки размыта.** Промпт (`content_analysis_prompt`, `lib/ai.php:404`): «61–80 хорошо; 81–100 отлично»,
   порог пула `RELEVANCE_THRESHOLD = 61`. Модель ставит почти всем 75/80/85:
   оценка 60–65 → **70–78% жалоб**; 75 (129 карточек) → 57% жалоб; 80 → 34%; 85 → 20%; 90+ → 0–7%.
3. **Форма поста не учитывается.** Поле `format` уже есть в анализе. У мемов `format = photo` (обычное фото, не мем):
   40 карточек, **0% лайков, 85% жалоб**. Карточки без подписи: 57% жалоб.
4. **Двач для мемов плох:** 182 карточки — лайк 10%, жалоба 63%. Telegram: лайк 45%, жалоба 21%.
5. **Популярность поста предсказывает лайк**, а в отбор не входит. Telegram отдаёт просмотры поста и медиану
   просмотров соседних постов канала (`engagement`): просмотры ≥ 1,3× медианы → **62–68% лайков**, жалобы 3–12%;
   < 0,7× → 31% лайков.
6. **Метки показывают вкус:** у карточек с первой меткой `humor.jokes` — 81% лайков, 0% жалоб; `humor.absurd` —
   34% лайков, 46% жалоб. Личный прогноз вкуса выключен (`PERSONAL_TASTE_ENABLED = false`, AUC 0.60).
7. Быстрая предпроверка (`screened_cache`) есть лишь у 52 карточек из 610 — по ней выводов не сделать.

**Простые правила на тех же 610 карточках (без модели):**

| Правило отбора | Осталось | Лайк | Дизлайк | Жалоба | Сохранено лайков |
|---|---|---|---|---|---|
| сейчас (оценка ≥ 61) | 93% | 37% | 31% | **30%** | 99% |
| оценка ≥ 80 | 67% | 42% | 36% | 20% | 83% |
| ≥ 80 + без «может/возможно» | 65% | 44% | 37% | 17% | 83% |
| + не `format=photo` | 63% | 46% | 37% | 16% | 83% |
| + не Двач | 50% | 55% | 37% | **7%** | 79% |
| + просмотры ≥ 0,7× медианы канала | 43% | 57% | 35% | 7% | 71% |

То есть **жалобы «не по теме» можно срезать с 30% до 7%, потеряв ~20% лайкнутого.** Дизлайки (~35%) этими
правилами не лечатся: это «по теме, но не смешно / не нравится» — для них части D и E.

## Что делаем

Части по порядку: 0 → A → B → C → D → E. После каждой — проверка; следующую не начинай, пока не прошла предыдущая.
Если упёрся — остановись и напиши, на чём.

## Общие правила

- **Не делай git commit.** Перед записью в базу: `cp data/posta.sqlite data/posta.sqlite.bak-quality`.
- **НЕ открывай сайт** (`http://localhost/...`) ни curl, ни браузером: каждая загрузка без куки создаёт пользователя
  и запускает парсер, который нельзя остановить без sudo. Всё — через `php` в CLI.
- **Модели.** Видеокарта 3 ГБ, на ней работает парсер пользователя. Полный анализ — только умная модель
  (`analysis_model()` / `SMART_MODEL`); **не переводи** его на быструю 2B ради скорости. Вызовы модели — только в
  части C (прогон оценки) и с указанным лимитом.
- Не меняй формат записей истории (`history_items.data`) — по ним считается качество. Новые поля можно добавлять.
- Пороги и списки — константами в `config.php` с комментарием «почему такое число» (ссылка на цифры выше).
- Код в стиле проекта: короткие функции, комментарии по-русски одной строкой.

## Часть A. Отчёт качества по истории (без модели)

`tools/quality_report.php` (CLI, только чтение) — то, что посчитано выше, для любой темы или группы тем
(`--topic "мемы и юмор"` сравнивает через `topic_same`/`topics_are_equivalent`, по умолчанию — все темы с ≥ 30
оценками):
- итог: лайк / дизлайк / жалоба;
- разрезы: оценка `relevance` (по точным значениям и корзинами), `format`, есть ли подпись, видео/картинка,
  площадка, первая метка, просмотры / медиана канала, реакции на 1000 просмотров, «оговорки» в `why_relevant`
  (регулярка — константа `ANALYSIS_HEDGE_RE`: `может|возможн|если |вероятно|потенциальн|можно использовать|подойти для`);
- **симуляция правил**: для набора правил (тех же, что в таблице выше, и тех, что ты добавишь в части B) — сколько
  осталось, доли, сколько лайков сохранено. Правила — те же PHP-функции, что будут работать в парсере (часть B),
  а не копия логики в отчёте.
- `--json` для машинного сравнения.

**Проверка:** цифры по мемам совпадают с таблицами выше (±1–2% — допустимо; сильно не так — разберись и напиши).
Сохрани вывод в `/tmp/quality-before.txt`.

## Часть B. Жёсткие правила отбора (без модели)

В `analyze_candidate` после ответа модели (и в одной функции `pool_admission(array $a, array $item, string $topic): ?string`
— причина отказа или `null`, чтобы её же звал отчёт из части A):
1. **Порог** `RELEVANCE_THRESHOLD` → 80 (обоснование — таблица). `PRESCREEN_THRESHOLD` оставь отдельной константой
   и не поднимай без данных (предпроверка оценивает иначе).
2. **Оговорки:** `why_relevant` совпал с `ANALYSIS_HEDGE_RE` → отказ «модель не уверена».
3. **Форма поста под тему:** список допустимых `format` для темы. Для юмора и мемов (ветка `humor`, её частные и
   темы-синонимы) `photo` не допускается (обычное фото без шутки). Для остальных тем — без ограничений, пока нет
   данных (если есть `topic_format()['kinds']` — бери оттуда).
4. **Площадка для темы по отзывам:** если у площадки по этой теме у этого пользователя ≥ 30 оценок и доля жалоб ≥ 50%
   (Двач в мемах — 63%), то её кандидаты идут в полный анализ не чаще 1 из 10 (найди, где очередь
   `build_candidate_queue` смешивает площадки, и снизь долю там, а не отбрасывай после анализа — так экономится
   модель). Пересчёт — раз в проход парсера. Это по пользователю, общий каталог не трогай.
5. В журнале парсера на каждый отказ — причина словами («порог 80: оценка 75», «модель не уверена: „может
   подойти для…“», «обычное фото, а тема — мемы»).

**Проверка:** `php tools/quality_report.php --topic "мемы и юмор"` — симуляция с новыми правилами: жалобы ≤ 10%,
сохранено лайков ≥ 75%. Если нет — подбери пороги **по отчёту**, а не на глаз, и опиши выбор.

## Часть C. Промпт оценки: доказательства вместо додумывания (модель, с лимитом)

1. Перепиши `content_analysis_prompt` и схему:
   - поля **до** оценки: `evidence` — что **именно видно или написано** в записи, что относится к теме (цитата
     надписи или предмет на картинке; нет — пустая строка); для тем юмора — `joke`: в чём шутка, одним предложением
     («подпись „я и вы“ к фото мышей» — не шутка; пусто, если шутки нет);
   - запрет додумывать: «оценивай только то, что есть в записи; „могло бы подойти“, „возможный контекст“ — значит
     не подходит»;
   - новая шкала с якорями-примерами для темы юмора и для обычной темы (0–30 не про тему или нет шутки; 31–60 тема
     есть, но слабо / шутка натянута; 61–85 явно по теме; 86–100 яркий пример темы) — примеры возьми из реальных
     жалоб и лайков отчёта (описания, без картинок);
   - **в коде**: `evidence` пустой → `relevance ≤ 40`; тема юмора и `joke` пустой → `relevance ≤ 40`.
2. Подними версию промпта в ключе кэша анализа (`analysis_cache_key`) — старые оценки не должны подмешиваться.
3. **Прогон на истории** `tools/quality_eval.php`: случайная выборка из истории пользователя по мемам — 20 лайков,
   20 дизлайков, 20 жалоб, у которых есть файл картинки в кэше медиа (`image_local`), только картинки (без видео,
   чтобы быстрее). Для каждой — новый анализ (без записи в кэш анализа и пул), вывод: старая оценка → новая,
   `evidence`, `joke`, прошла бы `pool_admission`. Итог: сколько жалоб теперь отсеяно, сколько лайков сохранено.
   **Лимит: 60 вызовов умной модели за запуск.** Запускай в фоне (`nohup … > /tmp/quality-eval.log`), с `nice -n 10`,
   и проверяй лог; модель медленная (до минуты на картинку) — это нормально.
   Цель: жалоб отсеяно ≥ 70%, лайков сохранено ≥ 80%. Не достиг — поправь промпт и прогони ещё раз
   (не больше 3 прогонов). В отчёт — таблица по всем прогонам.

## Часть D. Порядок карточек: популярность и источник

Сейчас пул сортируется по `relevance` (или `rating`, если включён вкус). Сделай итоговый балл карточки
`card_score(array $item, string $topic): float` и сортируй по нему (в `add_item_to_pool_safely` и везде, где пул
упорядочивается — найди все места):
- база — `relevance`;
- популярность: просмотры / медиана канала (`engagement`) — ≥ 2× → +10, 1,3–2× → +5, < 0,7× → −10; нет данных — 0;
- доля лайков источника у этого пользователя по теме (от 5 оценок): `(доля − 0,4) × 30`, ограничь ±15;
- константы в `config.php`; проверь отчётом (часть A, разрез по `card_score`), что верхняя треть по баллу лайкается
  заметно чаще нижней. Если нет — не включай этот пункт, напиши почему.

## Часть E. Вкус по меткам вместо выключенного прогноза

Простая и объяснимая замена `PERSONAL_TASTE`: доля лайков пользователя по первой метке карточки (`tags[0]`) в теме,
от 8 оценок по метке. В `card_score`: `(доля по метке − доля по теме) × 40`, ограничь ±15 (`humor.jokes` у этого
пользователя — 81% против 35% по теме → поднимется, `humor.absurd` — опустится). Проверь отчётом так же, как в D,
причём **честно**: считай долю по метке только по оценкам, сделанным **раньше** оцениваемой карточки (иначе
подглядывание в ответ). Не помогает — не включай.
