# Задача: умный автоподбор источников с годнотой и реестр проверенных источников

Ты работаешь в Go-проекте `/var/www/html/posta` (Posta), ветка `go-rewrite`. Владелец: «надо сделать умный поиск источников, который сам находит источники с годнотой. Пусть хранится список проверенных источников, чтобы те, что уже предлагались, не подбирались и не искались».

Задача большая. **Советуйся с Sonnet** (инструмент Agent, `model: "sonnet"`):
- перед частью A — покажи схему таблицы и план переноса старых данных;
- перед частью B — покажи формулу «годноты» и распределение бюджета проверок;
- если баг не поддаётся после двух попыток;
- в конце каждой части — попроси проверить `git diff` (корректность, гонки, миграция на живых данных, пропущенный украинский фильтр).
Sonnet только читает и советует; правки делаешь ты.

Перед началом:
- `git status` / `git diff`: в рабочей копии чужие незакоммиченные правки. Не откатывай их и не включай в свои коммиты (`git add -p`).
- Номера строк могли сдвинуться — ищи по именам функций.
- Рядом лежит `SEARCH_ENGINE_PROMPT.md` (широкая воронка и поиск по запросу). Если он уже выполнен, новые площадки поиска (Rutube, 9GAG, Pikabu…) и `PostSearchSuggest` у тебя уже есть — подключи их к реестру. Если не выполнен — не делай его работу, просто оставь в коде точку, куда они встанут.

## Правила проекта (обязательно)

- **Сборка и перезапуск:** `go build -o bin/posta ./cmd/posta && sudo systemctl restart posta`. HTML/CSS/JS работают сразу.
- **Живую БД руками не трогай.** Миграция — файлом `internal/db/migrations/0004_source_registry.sql` (следующий номер после 0003; проверь). Сначала прогоняй на dev Postgres (порт 55432) с копией живых данных, если владелец её даст, иначе — на dev-данных. Тесты — `go test ./internal/posta/...`, dev-сервер `POSTA_DEV=1` на 8097.
- **Модели:** через `u.LLM.Generate` с ролью, как в соседнем коде (`sourceReviewRequest`). Платные выключены — всё на бесплатных и локальных. Платных прогонов не запускай.
- **Никаких `confirm`/`alert`** в JS: только `ask()` из `js/core.js`.
- **Настройки поведения** — строки `Tunables` (`internal/posta/tunables.go`), группа «Подбор источников».
- **Не меняй решения владельца:** автодобавление выключено (`auto_add_score = 101`) — находки идут в предложения, решает владелец.
- **Украинский фильтр** (`UASourceBlocked`) — до любой проверки кандидата.
- Пиши как соседний код: короткие русские комментарии, `jx.M`, `u.Log(...)` на русском.

## Как сейчас (прочитано 2026-10-30, перепроверять не нужно)

Автоподбор — `internal/posta/discovery.go` (`runSourceDiscoveryLocked`), поиск кандидатов — `discovery_finders.go`.

- **Память о проверенных** — `d.Discovery["checked_at"]`: карта «`тема|source_id` → время» внутри общего каталога. Не больше `DiscoveryCheckedLimit = 1000` записей (старые вытесняются), через `DiscoveryRecheckDays = 30` дней источник проверяется снова. Хранится только время, без результата и без причины.
- `discoveryKnownIDs(d, topic)` пропускает кандидата, если он в каталоге, в решениях владельца (`d.Votes`) или в предложениях (`d.Suggestions`) **этой же темы** или проверен по этой теме за 30 дней. По другой теме тот же канал проверяется заново: запросы к сети, модель.
- `storeDiscoveredSource` → `added` / `suggested` / `rejected`. У отказа не остаются ни балл, ни причина, ни метрики. Отказ «пустой источник/не загрузилось» (`ErrDiscoveryMissing`) и отказ «не по теме» хранятся одинаково.
- **Оценка источника** (`evaluateSource`) проверяет только **соответствие теме** (текст подписей умной моделью, коллаж картинок). Годноту не проверяет никто: сколько людей реагирует, оригинальный ли контент, нет ли рекламы через пост, нравится ли такое владельцу.
- Аудитория (`DescribeSourceAudience`, `view_rate`, подписчики) и активность (`DescribeSourceActivity`, постов в неделю) считаются, но в балл почти не входят.
- **Семена** «похожих каналов» и снежного кома (`discoveryTopicSeeds`) — каталог и предложения темы по `score`. Источники, чьи посты владелец **лайкает**, не учитываются, хотя индекс уже есть: таблица `source_quality` (`internal/posta/source_quality.go`, миграции 0002–0003, лайк / «не знаю» / дизлайк по ключу источника).
- `DiscoveryOriginBonus` уже считает долю «да» владельца по виду находки (поиск, похожие, модель, ссылки…) и даёт ±10 к баллу. Но бюджет проверок (`discovery_checks = 40`) между видами не делится.

## Часть A — реестр проверенных источников (коммить отдельно)

1. **Таблица** `source_registry` (Postgres):
   - `source_id text PRIMARY KEY` — как `SourceIDFor(platform, id)`, нормализованный (нижний регистр, без `@`);
   - `platform`, `name`, `url`;
   - `first_seen_at`, `checked_at`, `check_count`;
   - `status`: `catalog` (в каталоге) · `suggested` (предложен, ждёт решения) · `owner_yes` / `owner_no` / `owner_maybe` (решение владельца) · `rejected` (модель: не по теме или не годнота) · `dead` (пустой, закрытый, удалён) · `failed` (не загрузилось — можно повторить) · `ukraine`;
   - `topics jsonb` — по каждой теме, где проверялся: балл темы, балл годноты, причина, время;
   - `metrics jsonb` — подписчики, `view_rate`, постов в неделю, последний пост, доля рекламы, доля репостов, средние реакции/пересылки;
   - `origin jsonb` — как нашли (вид находки, запрос, семя);
   - `sample jsonb` — до 8 последних постов в кратком виде (url, текст до 300 символов, картинка) — чтобы оценить источник для **другой темы без новых запросов к сети**.
   Индексы по `status` и `platform`.
2. **Перенос старых данных** в той же миграции или однократной командой при старте (с флагом в kv, как `PruneSourceDuplicates`): каталог (`catalog_sources`) → `catalog`; `source_votes` → `owner_*` по решению; `source_suggestions` → `suggested`; `discovery.checked_at` → `rejected` с пометкой «перенесено, причина неизвестна». Пересчитай, что сумма совпадает, и выведи числа в журнал сервера.
3. **Правило «не подбирать и не искать повторно»** — одна функция `u.RegistrySkip(sourceID, topic) (skip bool, reason string)`, её вызывают **все** пути, где появляется кандидат: каждый поисковик в `discovery_finders.go`, снежный ком, адреса от модели (`discoveryModelHandles`), авторы постов (`PostSearchAuthor`/`PostSearchSuggest`), поиск каналов по запросу (`RunQueryDiscovery`, `querySearchTelegramChannels`). Проверка — **до** любого сетевого запроса по кандидату.
   - `catalog`, `suggested`, `owner_*`, `dead`, `ukraine` — пропуск всегда, по любой теме: «уже предлагался» значит не предлагать снова никогда (так сказал владелец).
   - `rejected` по этой теме — пропуск. `rejected` по другой теме — **без сети**: оценка по сохранённому `sample` для новой темы (один вызов модели), результат — в `topics` реестра. Если сэмпл старше `registry_sample_days` (тунабл, 60) — пропуск.
   - `failed` — повтор не раньше чем через сутки, не больше 3 раз, потом `dead`.
   - Тунабл `registry_recheck_days` (по умолчанию 0 = никогда): через столько дней `rejected` можно проверить заново по сети. Владелец может включить сам.
   Убери из кода `d.Discovery["checked_at"]` и `DiscoveryCheckedLimit` — их заменяет реестр. `discoveryKnownIDs` переписать через реестр.
4. **Запись в реестр** — в `storeDiscoveredSource`, при голосе владельца за предложение (`source_ui.go`, где пишется `d.Votes`), при ручном добавлении источника (`SourceAddManual`), при удалении источника из каталога (`owner_no`, если владелец удалил сам), при заморозке мёртвого источника (`dead`), при блокировке украинского (`ukraine`).
5. **Вкладка «Источники» → «Проверенные».** Список реестра: поиск по имени, фильтры по статусу, площадке, теме; у записи — статус, баллы по темам, причина, метрики, откуда нашли. Действия: «Предложить снова» (вернуть в предложения), «Забыть» (удалить из реестра — тогда снова может найтись). Подтверждения — через `ask()`. API — новые действия в `internal/web` рядом с остальными действиями источников, ответ в формате соседних.
6. Тесты: `RegistrySkip` на всех статусах, перенос старых данных на фикстуре (`tools/fixtures/`), повтор `failed`.

Коммит: «Источники: реестр проверенных, без повторных находок».

## Часть B — умный автоподбор «с годнотой»

Цель: в предложения попадают источники, которые не просто «по теме», а с хорошим контентом — живые, с откликом аудитории, оригинальные и во вкусе владельца.

1. **Балл годноты** `SourceGoodness` (0–100) — отдельно от балла темы, хранится в реестре. Составляющие (веса — в `config`, итог объясняется строкой в причине предложения):
   - **отклик:** `view_rate` и реакции/пересылки на пост относительно подписчиков; сравнивай с медианой площадки и темы (свои медианы считай по реестру, а не выдумывай);
   - **жизнь:** последний пост не старше `content_max_age`, постов в неделю в разумных пределах (1–60; поток 200+ в неделю — агрегатор, минус);
   - **оригинальность:** доля репостов/пересылок из других каналов, доля постов-ссылок, одинаковые картинки с уже известными источниками (pHash есть в `collectKnownHashes`) — много совпадений = перезаливщик;
   - **реклама:** доля рекламных постов (`PostSearchIsAd`, метки «реклама», `erid`) — больше 30 % — сильный минус;
   - **вкус владельца:** одна оценка моделью сэмпла (до 6 постов, текст + коллаж, как `sourceImagesReview`) с примерами: 5 описаний недавних лайков и 5 дизлайков владельца по этой теме (из истории, поле `description`). Вопрос модели — «понравится ли владельцу», ответ 0–100 и короткая причина.
   Предложение: балл темы ≥ `suggest_score` **и** годнота ≥ `goodness_min` (тунабл, по умолчанию 55). Ниже — `rejected` с причиной «не годнота: …».
2. **Дешёвые фильтры до дорогих.** Порядок проверки кандидата: реестр → украинский фильтр → одна страница (название, описание, подписчики, последний пост) → отсев мёртвых/пустых/слишком мелких (порог подписчиков — тунабл, по площадке) → тема по тексту → метрики годноты → только потом вызов модели на вкус и коллаж. В журнале — на каком шаге отсеян каждый кандидат и сводка по шагам.
3. **Семена из того, что нравится.** `discoveryTopicSeeds`: первыми идут источники с высоким `source_quality` (лайки владельца) и `owner_yes`, потом каталог по `score`. От них — похожие каналы Telegram (`TelegramUserFindChannels(nil, similarTo)`), каналы, из которых они пересылают посты, и упомянутые/ссылочные (`SourceLinkedSources`). Пересылки: проверь, отдаёт ли их `TelegramPostsFromHTML` (на t.me/s есть «Forwarded from»); если нет — добавь поле `forwarded_from`. Источники с низким `source_quality` (много дизлайков) — анти-семена: их похожие получают минус к приоритету.
4. **Бюджет по видам находки.** Бюджет `discovery_checks` делится между видами находки (поиск по словам, похожие, пересылки, ссылки, модель, авторы постов, новые площадки) пропорционально доле «да» владельца по виду (`DiscoveryOriginReport`), с минимумом 10 % на каждый вид, чтобы новые виды тоже пробовались. Выведи в журнал распределение.
5. **Автоподбор сам.** Если у темы меньше `min_sources` живых источников, автоподбор запускается сам (это уже есть), а если предложения висят без решения — новые не копятся бесконечно: не больше `suggestions_pending_max` (тунабл, 60) на тему, сверх — лучшие по баллу, остальные остаются в реестре со статусом `rejected`, причина «очередь предложений полна» (их можно вернуть из «Проверенных»).
6. **Объяснение в предложении.** В `reason` предложения: тема N %, годнота N % (отклик, жизнь, оригинальность, реклама, вкус — по словам, коротко), откуда найден (семя/запрос).
7. Тесты: формула годноты на фикстурах (живой оригинальный канал, агрегатор с рекламой, мёртвый, перезаливщик); деление бюджета.

Проверка части B: `posta discovery-run <тема>` на dev (команда есть в `cmd/posta`) по темам «Мемы» и «Города»: в журнале видно шаги отсева и распределение бюджета; ни один кандидат из реестра не проверялся по сети повторно (посчитай и выведи); в предложениях у каждой находки есть годнота и причина. Повторный запуск сразу после первого не предлагает ни одного уже предложенного источника. Коммит: «Автоподбор: годнота источника, семена из лайков, бюджет по видам находок».
