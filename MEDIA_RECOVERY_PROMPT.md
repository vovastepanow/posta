# Задача: пропавшие файлы в «Предложке» — вернуть и не терять больше

Ты работаешь в PHP-проекте `/var/www/html/posta` (Posta: ИИ подбирает контент по теме и публикует в Telegram).

## Что случилось (уже выяснено, не перепроверяй с нуля)

В «Предложке» почти все плитки показывают «Файл недоступен» (CSS `.proposal-tile.is-broken` в `css/app.css`).

- У записей истории есть локальная копия (`image_local` / `video_local` вида `media/<32 hex>.<ext>`, файл в
  `MEDIA_CACHE_DIR` = `/var/lib/posta/media`) и исходная ссылка (`image` / `video`).
- У пользователя `b34cfe131b9ddea519d4cbd42c831fb5` **278 локальных файлов отсутствуют на диске** (166 записей из
  Telegram, 112 с Двача), все — у записей, оценённых 18–19 октября. Записи 22 октября — с файлами.
- Если локального файла нет, `content_for_display` подставляет исходную ссылку. Ссылки CDN Telegram
  (`cdn4.telesco.pe/file/…`) живут недолго и уже протухли; ссылки Двача умирают вместе с тредом. Отсюда «Файл
  недоступен».
- Механизм «достроить медиа из исходного поста» уже есть: `proposal_backfill_media` → `proposal_fetch_media` (берёт
  свежие ссылки со страницы `t.me/s/<канал>` или из JSON треда Двача) → `proposal_cache_media` (кладёт в кэш). Но он
  выбирает только записи **без** `media_cached`, а у пропавших `media_cached = true` — поэтому их никто не чинит.
- У профилей `a6adaaa5…` и `cf39dfa1…` (подняты из старых JSON) 36 записей со старым префиксом пути `media_cache/…` —
  `media_cache_path()` такие пути не распознаёт вовсе.

**Чем это опасно на будущее.** `media_cache_cleanup($records)` удаляет из `MEDIA_CACHE_DIR` всё, на что не ссылаются
переданные записи (обычно `all_users_pool_items()` — пул и история **всех** пользователей). Если ей передать пустой или
неполный список (пустая база, ошибка чтения, тестовая копия базы), она удалит весь кэш. Тестовые копии проекта (так
велят `*_PROMPT.md`: «скопируй проект во временную папку») берут `config.local.php` с **абсолютным** путём к настоящей
папке медиа — тест на копии базы работает с настоящими файлами.

Нужно:
1. **Защитить кэш** от массового удаления и тесты — от настоящей папки медиа.
2. **Вернуть файлы** записям, у которых они пропали, из исходных постов.
3. **В интерфейсе** — честное состояние и кнопка «Загрузить заново» вместо немого «Файл недоступен».

Делай части по порядку: A → B → C → D → E. Не начинай следующую, пока проверка предыдущей не прошла.

  `update_history_proposals`, `handle_proposal_hide`, `handle_proposals`), `lib/db_access.php`
  (`all_users_pool_items`, `history_update`), `lib/parser.php` (где вызывается `media_cache_cleanup`), `config.php`
  (`MEDIA_CACHE_DIR`, `MEDIA_CACHE_URL`), `tools/cli.php` (`backfill-proposals`, справка), `js/tabs.js` (плитки
  «Предложки», класс `is-broken`), `css/app.css` (`.proposal-tile`).
- **Не делай git commit.** Пользователь проверит изменения сам.
- **Не трогай файлы и функции, которые не названы в задаче.** Если без правки не названной функции не обойтись —
  сделай минимальную и упомяни её в отчёте.
- **Пиши в стиле проекта:** короткие функции, комментарии по-русски, без классов и новых библиотек.

- **Перед первым запуском PHP-кода после правок сделай копию базы:**

## Часть A. Защита (делается первой)

### A1. Папка медиа для тестов

В `config.php` путь к кэшу берётся из `$local['MEDIA_CACHE_DIR']`. Добавь переопределение переменной окружения —
**она важнее** `config.local.php`:
```php
define('MEDIA_CACHE_DIR', getenv('POSTA_MEDIA_CACHE_DIR') ?: ($local['MEDIA_CACHE_DIR'] ?? ROOT . '/media_cache'));
```
(сохрани текущий стиль строки; посмотри, как сейчас записан `define`).

Во всех `*_PROMPT.md` в корне проекта, где есть команда запуска теста на копии (`T=$(mktemp -d) && cp -r …`), добавь
перед `php "$T/tools/…"` создание пустой папки и переменную:
```
mkdir "$T/media" && POSTA_MEDIA_CACHE_DIR="$T/media" php "$T/tools/test_….php"
```
Сами тестовые скрипты (`tools/test_*.php`) в начале проверяют: `if (MEDIA_CACHE_DIR === '/var/lib/posta/media')
exit("Тест запущен с настоящей папкой медиа: задайте POSTA_MEDIA_CACHE_DIR\n");` — добавь в каждый существующий.

### A2. Предохранитель в `media_cache_cleanup`

Перед удалением посчитай, сколько файлов будет удалено (без учёта свежих по `MEDIA_CACHE_GRACE_SECONDS`). Если:
- список записей пуст, а в папке больше 20 файлов, **или**
- будет удалено больше `MEDIA_CACHE_CLEANUP_MAX_SHARE` (новая константа в `config.php`, `0.3`) от всех файлов папки,

— ничего не удаляй, напиши в `error_log` и через `cli_echo` строку «Кэш медиа: очистка остановлена — удалилось бы N из
M файлов. Проверьте базу; удалить принудительно: tools/cli.php media-cleanup --force» и верни 0.

Новый параметр `$force = false` снимает предохранитель. Команда `tools/cli.php media-cleanup [--dry-run] [--force]` —
печатает, сколько удалит, и удаляет (с `--force` — без предохранителя; без `--dry-run` и без `--force` — с
предохранителем).

### A3. Предохранитель на одиночные удаления

`media_cache_remove($url)` удаляет файл без проверки. Сделай так, чтобы она не удаляла файл, на который ещё ссылается
**любая** запись пула или истории **любого** пользователя (проверка по таблицам `pool_items` и `history_items`:
`data LIKE '%<имя файла>%'` — имя файла это 32 hex + расширение, ложных совпадений не будет). Это защитит от случая,
когда одна и та же картинка есть у двух пользователей, и один её «убирает».

**Проверка части A:**
```
php -l config.php && php -l lib/content.php && php -l tools/cli.php
POSTA_MEDIA_CACHE_DIR=/tmp/x php -r 'require "bootstrap.php"; echo MEDIA_CACHE_DIR, "\n";'   # /tmp/x
php tools/cli.php media-cleanup --dry-run
```
`media-cleanup --dry-run` на настоящей базе должен показать небольшое число (устаревшие файлы), не сотни.

## Часть B. Аудит

Команда `tools/cli.php media-audit [id пользователя]` (без id — все пользователи), **только чтение**. Для каждой
записи пула и истории проверяет все локальные пути (`media_cache_item_urls`, включая `gallery`) и печатает по
пользователю и коллекции:
- `файл на месте` / `файла нет` / `старый путь media_cache/ (файл есть)` / `старый путь media_cache/ (файла нет)`;
- для записей без файла — источник: `telegram` (есть `source_url` вида `https://t.me/<канал>/<номер>`), `2ch` (есть
  `board`, `thread_id`, `post_id`), `другое`.

Итоговая строка: сколько можно попробовать вернуть из источника.

**Проверка:** `php tools/cli.php media-audit b34cfe131b9ddea519d4cbd42c831fb5` — примерно 166 telegram + 112 2ch
«файла нет» (числа могли немного измениться).

## Часть C. Восстановление

### C1. Пометить записи на повторную загрузку

Команда `tools/cli.php media-repair [id] [--dry-run]`:
1. **Старый путь:** `media_cache/<имя>` → если файл `<имя>` есть в `MEDIA_CACHE_DIR` — заменить на
   `MEDIA_CACHE_URL . '/<имя>'`; если нет — очистить поле (как в п. 2).
2. **Файла нет:** очистить `image_local` / `video_local` (и такие же поля в элементах `gallery`), у записей коллекций
   «Предложки» (`PROPOSAL_COLLECTIONS`) снять `media_cached` и `media_checked` — тогда `proposal_pending()` подхватит их,
   и `proposal_backfill_media` скачает заново. У записей остальных коллекций (дизлайки, жалобы) только очистить поля
   — заново не качать, они не показываются.
3. Сохранять через `history_update` / `pool_update` с `$uid` (как `update_history_proposals`).
4. Печатать: исправлено путей N, помечено на загрузку M, очищено без загрузки K.

### C2. Загрузка

Используй существующую команду `tools/cli.php backfill-proposals <id>` — она вызывает `proposal_backfill_media`
пачками. Проверь, что после C1 она действительно подхватывает помеченные записи, и что:
- **Telegram:** `proposal_fetch_media` находит пост на странице канала и возвращает свежую ссылку картинки
  (`image`) — `proposal_cache_media` должна **скачать картинку**, а не только видео: прочитай функцию; если картинку она
  не сохраняет, когда `image_local` пустой, — допиши это (через `media_cache_store_image` или как устроено соседнее
  сохранение).
- **Двач:** тред умер → `proposal_fetch_media` вернёт пустой результат; такие записи прячет
  `proposal_prune_dead_threads` (`proposal_dead`), это правильное поведение.
- Если пост в Telegram удалён — запись остаётся без файла; отметь её `media_gone = true`, чтобы её не качали по кругу
  (посмотри, как `proposal_pending` выбирает записи, и исключи `media_gone`).

**Не запускай загрузку для настоящего пользователя целиком** — это сделает пользователь. Для проверки:
```
php tools/cli.php media-repair b34cfe131b9ddea519d4cbd42c831fb5 --dry-run
```
И одну запись вживую (это сеть, не модель — разрешено): выбери одну запись из Telegram без файла, вызови для неё
`proposal_fetch_media` + `proposal_cache_media` из `php -r` и убедись, что файл появился в `MEDIA_CACHE_DIR`, а запись
в базе **не менялась** (в `php -r` не сохраняй результат).

## Часть D. Интерфейс «Предложки»

Сейчас плитка с битой картинкой — серый прямоугольник «Файл недоступен». Сделай:
- Текст в плитке: «Файл пропал» и кнопка «Загрузить заново» (класс `proposal-refetch`), если у записи есть источник
  (Telegram или Двач), иначе только «Файл пропал». Ссылка «Пост ↗» на источник уже есть в карточке — оставь.
- Кнопка вызывает новое действие `proposal_refetch` (POST, `image` — ключ записи): сервер для одной записи вызывает
  `proposal_fetch_media` + `proposal_cache_media`, сохраняет запись (через `update_history_proposals`) и возвращает
  обновлённую запись через `content_for_display`, или `json_error('Пост в источнике удалён или недоступен.', 404)`.
  Не чаще раза в 10 секунд на пользователя (отметка в `kv`, ключ `proposal_refetch:<uid>`), иначе 429.
- Маршрут — в `index.php` (`POST`). Плитка после ответа перерисовывается.
- Над сеткой, если битых плиток больше 5: «У N записей пропали файлы» и кнопка «Загрузить все заново» — она вызывает
  новое действие `proposal_repair` (POST): то же, что `media-repair` из C1 для текущего пользователя, затем
  `proposal_backfill_async()` (уже показывает полосу прогресса «Предложки» — проверь, что прогресс виден).

Новые CSS-классы — с префиксом `proposal-`.

## Часть E. Проверка

Создай `tools/test_media.php` (только CLI, с проверкой из A1, что папка медиа не настоящая) и запусти на копии:
```
T=$(mktemp -d) && cp -r bootstrap.php config.php config.local.php secret.key.php lib handlers tools "$T"/ \
  && mkdir "$T/data" "$T/users" "$T/media" && sqlite3 data/posta.sqlite ".backup $T/data/posta.sqlite" \
  && POSTA_MEDIA_CACHE_DIR="$T/media" php "$T/tools/test_media.php"; rm -rf "$T"
```
Сценарии (файлы — маленькие PNG, созданные GD в тестовой папке медиа; тестовые пользователи — новые):
1. **Предохранитель:** 10 файлов в папке, `media_cache_cleanup([])` → ничего не удалено, вернула 0; с `$force` —
   удалены все (кроме свежих — сделай файлы «старыми» через `touch($path, time() - 3600)`).
2. **Доля:** 10 файлов, записи ссылаются на 5 → удалилось бы 50% > 30% → ничего не удалено; ссылаются на 8 → удалены 2.
3. **Общий файл:** у двух пользователей запись с одним `image_local`; `media_cache_remove` по нему → файл на месте.
4. **Аудит и ремонт:** запись «Предложки» с `image_local` на несуществующий файл и `media_cached = true` → после
   ремонта поле пустое, `media_cached` снят, запись попала в `proposal_pending()`. Запись-дизлайк → поле очищено, в
   `proposal_pending()` не попала.
5. **Старый путь:** `media_cache/<имя>` при существующем файле → путь стал `media/<имя>`.
6. **`media_gone`:** запись с `media_gone = true` не попадает в `proposal_pending()`.
7. В конце удали тестовых пользователей.

Плюс `php -l` изменённых PHP, `node --check` изменённых JS.
