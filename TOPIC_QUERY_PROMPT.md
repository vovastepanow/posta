# Задача: уточняющий запрос к теме подбора («Города» + «тюмень»)

Ты работаешь в проекте `/var/www/html/posta` (Posta). Ничего не коммить. Модель анализа не менять (только `SMART_MODEL`, qwen3.5-vision 9B),
**новых вызовов 9B на каждый пост не добавлять** — только поле в существующем ответе (видеокарта 1060 3 ГБ, 9B почти вся на CPU).
Тесты — на копии базы (`POSTA_DB_FILE=/tmp/posta-query.sqlite`, `POSTA_MEDIA_CACHE_DIR=/tmp/posta-query-media`). Не открывай приложение
в headless-браузере без нужды: свежая загрузка страницы создаёт пользователя и запускает парсер (стенды — см. `tools/stand/`).

Если параллельно выполняется `PRESCREEN_SOFTEN_PROMPT.md` (2B больше не судит тему, у 9B урезан ответ) — не конфликтуй с ним:
сначала проверь, применён ли он, и встраивайся в актуальную схему анализа.

## 1. Что хочет владелец

Тема задаёт **что** (Города, Футбол, Аниме, Бизнес), запрос сужает **про кого/про что именно**: «Города» + «тюмень», «Футбол» + «Зенит»,
«Аниме» + «Наруто», «Бизнес» + «кофейни», «Мемы» + «Шрек». Подбор показывает только записи, которые подходят и к теме, и к запросу.

**Вторая тема остаётся как есть** (`topic2`, поле `#topic2-field`, `search_topic_key()` = «первая + вторая») — её не удалять и не менять.
Запрос — третий, независимый параметр: «Города» + вторая тема «Природа» + запрос «тюмень» — допустимо.

## 2. Настройка и ключ поиска

- `lib/core.php:333` `default_settings()`: новое поле `query` = `''`. Нормализация (рядом с `topic2`, `:345`): обрезка, схлопывание пробелов,
  до `TOPIC_QUERY_MAX_LEN` (новая константа, 60) символов, без кавычек и `+`. Проверка `topic_save_denied()` — та же, что для тем.
- `current_query()` рядом с `current_topic2()`.
- `search_topic_key()` (`lib/core.php:362`) учитывает запрос: «тема[ + вторая] ? запрос» (разделитель — ` ? `, в `topic_parts()` он
  не должен попадать в части — поправь `topic_parts`, чтобы отрезал хвост ` ? …`). От этого ключа зависят пул, `screened_cache`,
  `topic_verdict_stats`, `analysis_cache_key` — проверь каждое место, где ключ режется или сравнивается с темой
  (`grep -n "search_topic_key\|topic_parts\|current_topic()" lib handlers`), и что смена запроса даёт новый пул, а возврат к старому
  запросу — старый пул.
- `topic_prompt_context()` (`lib/topics.php:239`) запрос в контекст темы не добавляет — он идёт отдельной строкой (п. 4).

## 3. Интерфейс

- `index.html:102`: под полем второй темы — поле запроса в том же стиле (`.topic2-field` → общий класс), значок 🔍 вместо «+»,
  placeholder «уточнение: город, команда, персонаж, бренд…». Поведение — как у второй темы (`initializeSecondTopic`, `js/content.js:373`):
  клик активирует, Enter/клик мимо сохраняет, Esc отменяет. Вынеси общее поведение в одну функцию, не копируй.
- Новый обработчик `save_query` рядом с `handle_save_second_topic` (`handlers/content.php:165`): сохранить, перезапустить парсер
  (`start_content_parser_if_needed(true)`), вернуть `query`. `settings`-ответ (`handlers/content.php:113`) отдаёт `query`.
- Лог в консоли: «Уточнение: «тюмень» — ищу в теме «Города» только про это.» / «Уточнение убрано.»
- `setCurrentTopic` (`js/core.js:96`) — третий аргумент `query`; везде, где тема показывается пользователю, запрос виден: «Города · тюмень».
- Мобильная ширина 390 px: поле не ломает раскладку.

## 4. Анализ поста (без нового вызова)

- В `content_analysis_prompt` (`lib/ai.php:378`) при непустом запросе — строка: «Уточнение пользователя: «тюмень». Подходит, только если
  запись именно про это (место, команда, персонаж, бренд) — по подписи, надписи на картинке или узнаваемым приметам. Тема без уточнения —
  не подходит.» Запрос — данные, не инструкции (как подписи постов).
- В схему (`content_analysis_schema`) — поле `query_match` (0–100) **только когда запрос задан** (иначе схема и кэш прежние).
- Итоговая оценка при запросе: `relevance = min(relevance, query_match)`. Порог принятия — прежний `RELEVANCE_THRESHOLD`.
- Дешёвая подсказка без модели: если запрос (или его словоформа) есть в подписи / в названии источника — это сильный признак.
  Сделай простое совпадение по основе слова (обрезка русских окончаний, латиница/кириллица: «тюмень», «тюмени», «тюменский», «tyumen»),
  функция `query_text_hit(string $text, string $query): bool`. Используй его (а) для порядка очереди — посты с совпадением идут на 9B первыми,
  (б) в промпте 9B как примету «в подписи упомянуто». Отсекать посты без совпадения **нельзя** — картинка без подписи тоже может подходить.
- `analysis_cache_key` (`lib/parser.php:549`) включает запрос.

## 5. Источники под запрос

Общие источники темы почти не пишут про Тюмень — без своих источников пул будет пустой.
- При новом запросе парсер сначала проверяет, сколько у пары «тема + запрос» своих источников; если меньше `TOPIC_QUERY_MIN_SOURCES`
  (новая константа, 3) — запускает подбор источников **по запросу**: поиск каналов в Telegram (`search_channels` в `tools/tg_user.py:180`,
  как в `run_source_discovery`) по строкам «тюмень», «тюмень + слова темы» (2–4 варианта; веб-поиск не использовать — он заблокирован
  капчей), похожие каналы найденных (`similar_channels`).
- Проверка найденного канала — та же, что у обычного подбора (после `PRESCREEN_SOFTEN_PROMPT.md` — один вызов 9B на канал), но в промпте
  к теме добавляется запрос: канал должен быть и по теме, и про запрос («Тюмень сегодня» — да; общий канал про города — нет).
- Одобренные каналы сохраняются в каталог с темой и отметкой запроса: у записи источника новое поле `queries` (список нормализованных
  запросов), рядом с `topics`. Каталог общий: следующий пользователь с «Города · тюмень» получает их сразу.
- Сбор постов для пары «тема + запрос»: сначала источники с этим запросом, потом обычные источники темы (там 9B отсеет не-тюменское).
- Блокировка от параллельного подбора (`try_lock` в `run_source_discovery`) — ключ включает запрос.
- Лимит: не больше `TOPIC_QUERY_DISCOVERY_PER_DAY` (новая константа, 10) новых запросов с подбором источников на пользователя в сутки
  (паттерн — `source_add_quota_take`, `lib/source_add.php:64`). Сверх лимита — подбор только из имеющихся источников и сообщение в консоль.

## 6. Тесты (новый `tools/test_topic_query.php` + существующие)

- Нормализация: «  Тюмень  » → «Тюмень», длина, запрещённые слова.
- `search_topic_key()`: тема / тема + вторая / тема + запрос / все три; `topic_parts()` не захватывает запрос.
- `query_text_hit`: «тюмень» находит «В Тюмени открыли…», «тюменский», «Tyumen»; не находит «Тюлень».
- Схема анализа без запроса не изменилась (сравни JSON схемы), с запросом есть `query_match`; `relevance = min(...)`.
- Ключ кэша анализа разный для разных запросов.
- Существующие: `test_discovery.php`, `test_discovery_names.php`, `test_source_posts.php`, `test_adult.php` — зелёные.
- Ручная проверка на копии через CLI (без браузера): тема «Города», запрос «тюмень» — подбор источников находит тюменские каналы,
  парсер принимает посты про Тюмень и отклоняет посты про другие города с причиной в консоли. Приложи 5 строк консоли в отчёт.
