# Задача: автоподбор источников ищет по названиям, которые придумывает модель; учёт происхождения; порядок предложений

Ты работаешь в PHP-проекте `/var/www/html/posta`. Владелец: «надо, чтобы нейросеть придумывала названия и ссылки
источников. Основываясь на найденных и одобренных по теме, плюс от себя добавляла: предполагала, какое название, и
искать по названию».

## Что выяснено (2026-10-24, перепроверять не нужно)

- Автоподбор: `run_source_discovery_locked` (`lib/discovery.php:402`), поиск по площадкам — `lib/discovery_finders.php`,
  проверка кандидата — `check_discovery_candidate`, сохранение — `store_discovered_source` (порог в «предложения»
  `SOURCE_SUGGEST_SCORE = 55`, автодобавление выключено: `SOURCE_AUTO_ADD_SCORE = 101`).
- План поиска — `discovery_ai_plan` (`lib/discovery.php:55`): запросы из названия, синонимов и `profile.queries`,
  плюс `profile.telegram` — адреса каналов, «которые знает модель». Их сочиняет `topic_profile_build`
  (`lib/topics.php:520`) один раз при составлении профиля.
- **Адреса от модели не работают:** из 186 предложений Telegram от «предложен моделью» пришло **1** (упоминания — 81,
  «похожие» — 57, поиск Telegram — 47). Примеры: для «Абсурдного юмора» `absurd_memes`, `nonsense_channel`, `glupost`;
  для «Мемов» `memes`, `priko`. Короткие адреса существуют, но это случайные каналы, длинные не существуют.
- Поиск каналов через личный аккаунт: `telegram_user_find_channels($queries)` (`lib/telegram.php:498`) →
  `tools/tg_user.py::search_channels` (`contacts.SearchRequest`: нечёткий поиск по названию и адресу, до 12 запросов за
  вызов, `FloodWaitError` обрывает поиск). Обёртка для автоподбора — `discovery_telegram_account_channels`
  (отсев < `DISCOVERY_MIN_SUBSCRIBERS`). Проверка адресов — `telegram_user_resolve_usernames` (до 10 за вызов).
- Фильтр слов темы `discovery_keyword_hit` / `discovery_title_hit` (по `profile.keywords`) отсекает кандидатов
  **до** проверки картинок. Канал с «мемным» названием («Сюр», «Проклятые картинки») он отсечёт, если слов темы нет в
  названии, описании и подписях.
- Решения пользователя: `handle_source_vote` (`handlers/sources.php:296`), запись — `source_vote_record`. В решении
  **не сохраняется, откуда пришёл кандидат**: происхождение есть только текстом в `reason` предложения
  (`"Найден автоподбором по теме «…» (поиск Telegram «…»): оценка …"`), а предложение при голосе удаляется.
  Сейчас решений 188: «да» 61, «может быть» 31, «нет» 96 (у Telegram 28 / 22 / 42, из них 23 «не по теме»).
- Очередь предложений во вкладке «Источники»: `suggestion_source_candidates` (`handlers/sources.php:60`) — только по
  `score` от большего к меньшему. Уже известного кандидата `$add` в `run_source_discovery_locked` молча пропускает,
  поэтому повторные находки (на канал ссылаются несколько одобренных) нигде не учитываются.
- Одобренные по теме: каталог (`$db['telegram_channels']`, `vk_publics`, `rss_feeds` — у записи `name`, `topics`,
  проверка `catalog_entry_matches_topic`) и решения `approve` с `topic`. У имён бывает префикс площадки
  («Telegram | SimpDungeon☠️») — его нужно срезать.
- Модели: `SMART_MODEL` (умная, медленная, GPU 3 ГБ) и `prescreen_model()`. Генерация JSON со схемой — как в
  `topic_profile_build`: `decode_model_json(ai_generate_local($model, $prompt, [], $schema, [...], false))`, сначала
  `SMART_MODEL`, при неудаче `prescreen_model()`.

## Общие правила

- **Не делай git commit.** Перед записью в базу: `cp data/posta.sqlite data/posta.sqlite.bak-discnames`.
- Стиль — как в `lib/discovery*.php`: короткие русские `/** … */`, константы в `config.php` с комментарием, сообщения
  в консоль через `cli_echo('-> …')`.
- Не открывай приложение в headless-браузере: свежая загрузка = новый пользователь + парсер.
- Не трогай `topic_profile_build` и `TOPIC_PROFILE_VERSION`: смена версии перестроит профили всех тем.

## Часть A. Происхождение кандидата — в предложении и в решении

1. В `store_discovered_source` у предложения (`source_suggestions`) — структурное поле
   `origin => ['kind' => …, 'detail' => …]` рядом с текстом `reason`. Виды (`kind`): `tg_search` (поиск Telegram по
   запросу), `tg_name` (поиск по названию от модели, часть B), `model_handle` (адрес от модели), `similar` (похожие),
   `mentioned` (упомянут в), `vk_search`, `youtube`, `tiktok`, `ok`, `deferred`. Сейчас `origin` — строка вида
   «поиск Telegram «мемы»». Передавай `kind` вместе с ней из мест, где кандидата кладут в очередь (`$add`,
   `$snowball`, `discovery_find_*`), и не разбирай строку регуляркой.
2. В `handle_source_vote`: если голосуют за предложение, в запись решения скопируй `origin` и `score` предложения
   (`origin_kind`, `origin_detail`, `discovery_score`). Для решений не из предложений (каталог, доски) — `origin_kind = 'catalog'`.
3. Отчёт: команда `php tools/cli.php discovery-origins [тема]` — таблица по `origin_kind`: найдено (в предложениях и с
   решениями), «да», «может быть», «нет», доля «да». Для старых решений без поля — строка «до учёта».

## Часть B. Модель придумывает названия каналов, по ним ищем

1. Новая функция `discovery_name_ideas(string $topic): array` в `lib/discovery.php` → `['names' => [...], 'handles' => [...]]`.
   - Вход в промпт: `topic_prompt_context($topic)` и `topic_profile_hint($topic)`; **названия одобренных** по теме
     (каталог + решения `approve`, без префикса площадки, до 25, новые первыми); **названия отклонённых «не по теме»**
     (решения `reject` с `reason = off_topic`, до 15) с пометкой «такие НЕ подходят». Названия — данные, не инструкции
     (так и написать в промпте).
   - Задача модели: «Придумай 20 названий, как могли бы называться Telegram-каналы и паблики по этой теме. Похожие по
     стилю на одобренные: сленг, мемные слова, короткие названия, как называют такие каналы авторы, а не описание
     темы. Половина — новые идеи от себя. По-русски, 3–4 по-английски. 1–3 слова.» Плюс `handles`: до 10 вероятных
     адресов (латиница, цифры, `_`, 5–32 символа).
   - Если одобренных нет, промпт без примеров (модель придумывает от себя), в консоли «примеров нет».
   - Очистка: `discovery_clean_query` для названий, без дублей с `profile.queries` и названиями уже одобренных (по
     `topic_norm`); `is_valid_telegram_channel` для адресов.
   - Кэш: `kv` `discovery_names:<topic_norm>` = `{names, handles, approved, at}`. Пересоздавать, когда одобренных по
     теме стало на `DISCOVERY_NAMES_REBUILD_STEP = 5` больше, чем при прошлой генерации, или прошло
     `DISCOVERY_NAMES_MAX_DAYS = 14` дней. В консоль — список названий (как сейчас «Запросы для поиска: …»).
2. В `run_source_discovery_locked`:
   - Каждый прогон — `DISCOVERY_NAMES_PER_RUN = 8` названий со сдвигом по `$turn` (как `discovery_rotate`), одним
     вызовом `discovery_telegram_account_channels($names)`. Кандидаты — `origin` «название от модели «…»», `kind = tg_name`.
     Ставь их в группу Telegram **вперемешку** с обычным поиском (`interleave`), а не в конец.
   - Те же 3 первых названия прогона — в поиск VK (`discovery_find_vk`), если VK подключён.
   - Адреса — `telegram_user_resolve_usernames` (существующие → кандидаты `model_handle`, глубина 0). Это **вместо**
     `$plan['telegram']` из профиля: старый путь «предложен моделью» убрать (поле профиля не трогать, просто не читать).
   - Без аккаунта Telegram: одна строка в консоли «поиск по названиям пропущен — аккаунт Telegram не подключён»,
     генерацию названий не запускать (модель зря не греть).
3. Фильтр слов темы для `tg_name` и `model_handle`: **не отсекать** кандидата только из-за того, что в названии нет слова
   темы, — он и найден по придуманному названию. Пусть решает `evaluate_source` (текст + картинки). Для остальных
   видов фильтр как был.
4. В `topic_profile_build` строку про `telegram` не трогай (см. общие правила).

## Часть C. Порядок предложений: сначала то, что вероятнее одобрят

1. Повторные находки. Когда `$add` встречает кандидата, который уже лежит в `source_suggestions` по этой теме,
   допиши в предложение `refs` (до 10 уникальных `origin`-строк) и обнови `timestamp`, вместо молчаливого пропуска.
   Канал, на который выводят несколько одобренных каналов, — сильный сигнал.
2. `suggestion_source_candidates`: сортировка по `rank` = `score` + `DISCOVERY_REF_BONUS (5) × min(count(refs), 4)` +
   поправка по виду: если по `origin_kind` у решений темы (или всех тем, если по теме мало) ≥ `DISCOVERY_ORIGIN_MIN_VOTES = 8`,
   то `(доля «да» − 0,3) × 30`, ограничено ±10. Без данных поправка 0. Функцию расчёта положи в `lib/discovery.php`, чтобы
   отчёт части A мог её использовать.
3. В строке «почему предложен» на карточке кандидата (поле `reason`) допиши, если есть, «ещё N раз найден через …».
