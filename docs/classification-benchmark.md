# Проверка классификации v2

> **Архив исследования (ноябрь 2026).** Python-скрипты, упомянутые ниже, удалены из Posta. Примеры команд сохранены только для истории измерений и больше не предназначены для выполнения. Работающий сервис и автодеплой используют Go, JavaScript и Bash.


Это отдельный инструмент подготовки и оценки, не изменение рабочего сервиса.
Он не читает ключ API, не отправляет запросы моделям и не пишет в базу. Старые
прогоны и их эталоны остаются неизменными. Новая разметка версионирована отдельно.

## Подготовка

```sh
GOCACHE=/tmp/posta-go-cache python3 tools/classification_bench.py prepare \
  --snapshot data/backups/classification-audit-v14-20261112/snapshot.jsonl \
  --old-cases data/backups/classification-pilot-20261112/cases.json \
  --media-root /var/lib/posta/media \
  --output data/backups/classification-benchmark-v2-20261112
```

Новый каталог содержит полный сохранённый текст поста и доступный `article_text`:
ограничения 1800 символов больше нет. Если статья уже содержится в тексте поста,
её копия не дублируется. Несохранённая статья по внешней ссылке не считается
прочитанной; автоматического скачивания страниц здесь нет.

Тип материала определяется по самой записи, а не по прежнему эксперименту.
Для видео копируется **полный оригинальный файл**, проверяются его длительность
и звуковые потоки, извлекается полный WAV без обрезки по времени. Нет файла или
полной звуковой дорожки — вход отмечается неготовым; подмена заголовком или
обложкой запрещена. Реальные субтитры и речь не выдумываются из поля `captions`.
Поле `captions` в данных Posta часто содержит обычную подпись к посту.

Для модели с поддержкой видео и звука запрос включает `input_video` и отдельный
`input_audio`. Модель, не поддерживающая звук, требует полной расшифровки речи;
иначе сборка запроса завершается ошибкой. Можно передать `--transcript-dir`:
каждый `<id>.json` содержит `video_sha256`, `complete: true`, `text`. Расшифровка
должна соответствовать сохранённому ролику. Локальное распознавание речи в текущем
окружении не установлено; новые модели для него не скачивались.

Файлы, тексты, дерево и эталон фиксируются контрольными суммами. Старые ответы
не могут незаметно считаться ответами на исправленные входы. Существующий каталог
набора не перезаписывается: для новой редакции нужен новый каталог.

## Построение запроса без отправки

```sh
python3 tools/classification_bench.py request \
  --prepared data/backups/classification-benchmark-v2-20261112 \
  --id 17891 --model google/gemini-2.5-flash-lite \
  --modalities text,image,video,audio \
  --stage describe --output /tmp/posta-description-request.json
```

Это **только локальный файл**, не платный вызов. Возможности модели должны быть
взяты из её каталога. Форматы соответствуют документации OpenRouter:
[видео](https://openrouter.ai/docs/guides/overview/multimodal/videos),
[звук](https://openrouter.ai/docs/guides/overview/multimodal/audio).
Совместимость конкретного поставщика с таким запросом ещё не проверялась вызовом.

`describe` не получает дерева, старых меток или ожидаемого ответа: возвращает смысл
публикации, предполагаемую тему и достаточность содержания. `classify` требует
`--candidates` с 3–5 ключами, полученными поиском; передаёт определения и границы
только этих подтем. Родительские рубрики не разрешены. Пустой ответ при отсутствии
подходящего кандидата допустим; принудительный выбор ближайшего запрещён.

## Эталон и оценка

`tools/fixtures/classification_reference_v2.json` — предварительный эталон,
не подтверждённый пользователем. Для РТИ (17900) обязательность «Инженерии» и запрет
«Предпринимательства» сняты: весь пример отмечен спорным и исключён из строгой
оценки. Для ТН ВЭД (17902) «Логистика» остаётся основной, «Налоги» отмечены спорным
дополнением и автоматически не считаются лишней меткой.

Оценка хранит отдельно, без сведения к одному «неправильно»:

- `wrong_topics`: неподтверждённая тема вместо ожидаемой либо явно запрещённая тема;
- `extra_topics`: неподтверждённое дополнение при найденной ожидаемой теме;
- `missing_topics`: пропущенные обязательные темы;
- `too_general`: подходящая родительская рубрика вместо конкретной подтемы;
- `disputed_topics` / `reference_review_needed`: редакционный спор;
- `abstained`: модель явно сказала, что содержания недостаточно;
- `transport_error`: модель недоступна (429, таймаут и т. п.);
- `invalid_response` / `invalid_labels`: неисправный ответ;
- `input_incomplete`, несовпадение входа и `not_evaluated`: проблемы подготовки
  или отсутствующая проверка.

Измерения могут пересекаться: неверная тема одновременно означает пропуск нужной.
Ошибка поставщика не является отказом модели или отрицательным вердиктом. Пустые
метки при `sufficient=true` — явный отрицательный вердикт, а не отказ.
Неполные входы и спорные эталоны исключены из основных счётчиков тематических
ошибок. Точный итог также исключает предсказания со спорными дополнениями.

Для `score` нужен один JSONL-файл на модель, одна строка на запись с `id`,
`input_fingerprint`, `reference_sha256` из сохранённого запроса и `answer`
(`sufficient`, `topics`) либо `error`. Все неподанные записи явно учитываются
как `not_evaluated`. Неизвестные/повторные ID отвергаются.

```sh
python3 tools/classification_bench.py score --prepared <каталог-набора> \
  --predictions <ответы.jsonl> --output <оценка.json>
```

`rescore-archive --prepared ... --archive ... --output ...` перечитывает старые
ответы без повторного запуска старых скриптов. Берётся первое пригодное решение,
включая отказ, а не наиболее удачная попытка. Все попытки сохраняются отдельно.
Пришедшие на другие, неполные входы ответы не входят в новую точность. Это
диагностика истории, а не новый прогон исправленного набора.

Проверка инструмента:

```sh
python3 -m unittest discover -s tools -p 'test_classification_bench.py' -v
GOCACHE=/tmp/posta-go-cache go test ./tools/classification-taxonomy
```

## Поиск кандидатов v3 и достаточность содержания

Запрос `describe` теперь возвращает два отдельных признака:
`topic_identifiable` (понятна основная тема) и `details_complete` (хватает всех
подробностей). Например, сообщение о налоговой экономии компании может иметь
первый признак true, а второй false. Для выбора темы не требуется знать весь
механизм экономии. Из этого не следует право додумывать недостающие события.

`tools/classification_shortlist.py` нормализует новые описания и прежние ответы.
Прежний `sufficient=false` неоднозначен: его **нельзя** автоматически заменить
на `topic_identifiable=true`. Такой ответ остаётся ожидающим уточнения; уже имеющийся
текст описания можно использовать только для диагностической проверки поиска.

Поиск получает только описание и предположенную тему своими словами. Эталон,
старые метки, номер записи и ответы прежнего классификатора в ранжировании
не участвуют. Дерево экспортируется вместе с существующими синонимами и поисковыми
формулировками. Отрицательные границы из `hint` не индексируются как положительные
признаки. Предположенная тема и подробное описание сравниваются отдельно, чтобы
длинное описание не заглушало короткую формулировку предмета. Итог объединяет
смысловую близость, поиск по словам и до двух однозначных совпадений названия или
синонима именно в предполагаемой теме. Кандидат не становится подтверждённой меткой.

Алгоритм и веса записываются до оценки. Векторный расчёт возможен только через
локальный `127.0.0.1:11434`, используется уже установленная `bge-m3:latest`.
Кэш привязан к точным входам; повтор с тем же кэшем не вызывает модель заново.
Загрузка моделей и облачные запросы не предусмотрены.

```sh
GOCACHE=/tmp/posta-go-cache go run ./tools/classification-taxonomy > /tmp/posta-topics.json
python3 tools/classification_shortlist.py rank \
  --descriptions data/backups/classification-v2-run-20261112/descriptions.json \
  --taxonomy /tmp/posta-topics.json --cache /tmp/posta-vectors-v3.json \
  --output /tmp/posta-ranked-v3.json
python3 tools/classification_shortlist.py evaluate --ranked /tmp/posta-ranked-v3.json \
  --reference tools/fixtures/classification_reference_v2.json \
  --baseline data/backups/classification-v2-run-20261112/summary.json \
  --output /tmp/posta-retrieval-score-v3.json
```

`rank` не имеет параметра эталона. Только отдельный `evaluate` читает ожидаемые
метки. В итогах сохраняются пропущенные записи, все необходимые темы для записей
с несколькими метками и сравнение на одинаковом подмножестве. Эта проверка не
доказывает качество последующего выбора или работу на новых данных.

Проверки обоих инструментов:

```sh
python3 -m unittest discover -s tools -p 'test_classification_*.py' -v
```
