# Задача: своя очередь публикаций и расписание по слотам

Ты работаешь в PHP-проекте `/var/www/html/posta` (Posta: ИИ подбирает контент по теме и публикует в Telegram).

**Делается после `CHANNELS_PROMPT.md`** (таблица `channels`, `telegram_connection($uid, $channel_id)`). Проверь, что
она сделана: `sqlite3 data/posta.sqlite ".schema channels"` должен показать таблицу. Если нет — остановись и
сообщи пользователю.

Сейчас отложить пост можно только через «Отложенные» самого Telegram: для этого пользователь подключает личный аккаунт
(Telethon, `tools/tg_user.py`). Без аккаунта — только «опубликовать сразу». Для ВК и других площадок такого механизма
нет вовсе. Нужно:

1. **Своя очередь:** отложенный пост хранится у нас и в назначенное время уходит через бота. Аккаунт для этого не нужен.
2. **Расписание канала:** слоты по дням недели («пн–пт 10:00, 14:00, 19:00; сб–вс 12:00») и кнопка «В ближайший
   свободный слот».
3. **Надёжность:** повтор при сбое, пост не уходит дважды, пользователь узнаёт о провале.

**Почему «Отложенные» Telegram остаются.** Сайт сейчас работает на домашнем компьютере. Пост из «Отложенных» Telegram
выйдет, даже если компьютер выключен, а из нашей очереди — нет. Поэтому: если у пользователя подключён личный аккаунт —
по умолчанию пост ставится в «Отложенные» Telegram (как сейчас), а в редакторе есть выбор «Через очередь Posta».
Без аккаунта — только наша очередь. Существующий путь через аккаунт **не ломай и не переписывай**.

Делай части по порядку: A → B → C → D → E → F. Не начинай следующую, пока проверка предыдущей не прошла.

## Часть A. Модель данных

### A1. Посты нашей очереди — в существующей таблице `outbox`

Новые статусы поста (поле `status` таблицы и такое же поле в `data`):
- `queued` — ждёт времени;
- `sending` — публикатор взял его и отправляет;
- `failed` — все попытки исчерпаны, пост остаётся в очереди с текстом ошибки, пока пользователь его не удалит или не
  повторит.
Отправленный пост из очереди **удаляется** и попадает в журнал опубликованных (`telegram_log_published`), как сейчас
делает `telegram_settle_native_posts` для статуса `telegram`.

Поля записи (`data`): `id` (12 hex, как в `telegram_record_native_post`), `created_at`, `publish_at`, `channel`
(id канала), `text`, `media` (`[{kind, name, path, width, height, duration}]` — то, что вернула
`telegram_prepare_media`, но с путями в постоянной папке, см. A2), `status`, `attempts`, `error`, `next_try_at`,
`slot` (true — поставлен в слот расписания), `source_key` (ключ записи пула/истории, если пост из подборки; иначе '').

**Важно про `outbox_update`:** она перезаписывает все строки пользователя (`DELETE` + `INSERT`). Публикатор меняет
статусы прямо в строке (`UPDATE outbox SET status = ?, data = ? WHERE id = ?`) внутри `db_tx`, а `outbox_update`
тоже в `db_tx` — значит, они не пересекаются. Но `outbox_update`, вызванная **после** того как публикатор взял пост,
не должна вернуть ему старый статус: в мутаторах всегда работай с тем, что пришло на вход, а не с заранее прочитанной
копией.

### A2. Где лежат файлы отложенных постов

Сейчас медиа готовятся во временной папке (`telegram_work_dir`) и удаляются после отправки. Для нашей очереди файлы
нужно хранить до публикации. Кэш медиа (`MEDIA_CACHE_DIR`) не годится: его чистит `media_cache_cleanup`, удаляя всё,
на что не ссылаются пул и история.

- Папка поста: `data/outbox/<id поста>/` (у `data/` уже есть `.htaccess` с запретом доступа — проверь).
  Функция `outbox_media_dir($post_id)` в `lib/telegram.php`.
- При постановке в очередь медиа готовятся **сразу** (`telegram_prepare_media(..., 'bot')` — проверка форматов и
  перекодирование происходят при постановке, а не в момент публикации), затем папка с готовыми файлами переносится в
  `data/outbox/<id>/`, пути в `media` — уже оттуда.
- Удаление поста из очереди (отмена, успешная отправка) удаляет и папку (`remove_dir`).
- Команда `tools/cli.php outbox-gc`: удаляет папки `data/outbox/*`, для которых нет поста в `outbox`, и печатает число.

### A3. Расписание канала

Миграция со **следующим свободным номером**:
```sql
ALTER TABLE channels ADD COLUMN schedule TEXT NOT NULL DEFAULT '{}';
```
Формат `schedule` (JSON):
```json
{"tz": "Asia/Yekaterinburg", "jitter": 10, "slots": {"1": ["10:00", "14:00", "19:00"], "6": ["12:00"]}}
```
- `tz` — часовой пояс пользователя (браузер присылает `Intl.DateTimeFormat().resolvedOptions().timeZone`; на сервере
  проверка через `in_array($tz, DateTimeZone::listIdentifiers(), true)`, иначе — `date_default_timezone_get()`);
- `slots` — ключ: день недели ISO (`1` — пн … `7` — вс), значение: отсортированный список `ЧЧ:ММ` без повторов, не
  больше 24 слотов в день;
- `jitter` — случайный сдвиг времени публикации в минутах (0–30): посты не выходят в одну и ту же секунду каждый день,
  как у ботов. Сдвиг выбирается **один раз при постановке** и сохраняется в `publish_at`, чтобы пользователь видел
  точное время.

Функции в `lib/telegram.php`, раздел `// ---- Расписание канала ----`:
```php
/** Расписание канала с проверкой и значениями по умолчанию (пустые слоты, jitter 0, tz сервера). */
function channel_schedule(array $channel): array { ... }

/** Проверить и сохранить расписание. Ошибки формата — InvalidArgumentException с понятным текстом. */
function channel_schedule_save($channel_id, array $schedule, $uid = null): array { ... }

/**
 * Ближайший свободный слот канала после $after (unix time): слот занят, если на это время (± 1 минута, до сдвига) уже
 * стоит пост этого канала в статусе queued/sending/telegram. Ищем не дальше 60 дней. null — слотов нет.
 * Возвращает ['slot_at' => время слота, 'publish_at' => время со сдвигом jitter].
 */
function channel_next_slot(array $channel, $after, array $queue): ?array { ... }
```
- Слот считается в часовом поясе `tz` (`DateTimeImmutable` с `DateTimeZone`), учитывая переход на летнее время там,
  где он есть.
- Слот раньше чем `now + TELEGRAM_MIN_DELAY_SECONDS` не годится.
- Чтобы занятость слота определялась точно, храни в посте `slot_at` (время слота **до** сдвига).

```
php -r 'require "bootstrap.php"; echo db_value("pragma user_version"), "\n";'
```

## Часть B. Постановка в очередь

### B1. `handle_telegram_publish` — новый режим

Новое поле запроса `mode`:
- `now` — опубликовать сразу (как сейчас без `scheduled_ts`);
- `native` — в «Отложенные» Telegram через аккаунт (как сейчас со `scheduled_ts`);
- `queue` — в нашу очередь на `scheduled_ts`;
- `slot` — в нашу очередь в ближайший свободный слот канала (`scheduled_ts` не нужен).

Если `mode` не пришёл — поведение как сейчас (совместимость): `scheduled_ts` есть → `native`, нет → `now`.
Для `native` без подключённого аккаунта — прежняя ошибка. Для `slot` без слотов в расписании —
`json_error('У канала не настроено расписание: «Соцсети» → канал → «Расписание».', 422)`.

Проверки до подготовки медиа — те же, что сейчас (фильтр 18+, `billing_post_denied`, лимиты времени). Для
`queue`/`slot` `billing_post_denied($scheduled = true)` — отложенный пост.

Постановка (`queue`/`slot`): подготовить медиа во временной папке → сохранить пост в `outbox` со статусом `queued` →
перенести папку в `data/outbox/<id>/` → `billing_post_used()` → ответ
`ok(['scheduled' => true, 'id' => …, 'publish_at' => …, 'native' => false, 'channel_title' => …])`.
Если перенос папки не удался — удалить пост из `outbox` и вернуть ошибку (не оставлять пост без файлов).

### B2. Отмена и повтор

- `handle_telegram_cancel` — для `queued` и `failed` удаляет пост и его папку; для `sending` —
  `json_error('Пост уже отправляется — отменить нельзя.', 409)`. Путь для `telegram` (через аккаунт) не меняй.
- Новое действие `telegram_retry` (POST, `id`): пост `failed` → `queued`, `attempts = 0`, `error = ''`,
  `publish_at = max(publish_at, now + 60)`. Маршрут добавь в `index.php`.
- Новое действие `telegram_reschedule` (POST, `id`, `publish_at` или `slot: true`): для `queued` — новое время с теми
  же проверками, что при постановке.

## Часть C. Публикатор

### C1. `tools/publisher.php` — CLI-скрипт

Запускается cron раз в минуту (пользователь добавит сам, см. отчёт) и из страховки C3.
- Только CLI (`PHP_SAPI !== 'cli'` → 403, как в `tools/cli.php`).
- Одна копия: `try_lock(USERS_DIR . '/.publisher.lock')`; занято — тихо выйти.
- Вызывает `outbox_process_due(time(), 'outbox_send_post')` и печатает строку итога (`отправлено N, ошибок M`) только
  если что-то было.
- Не дольше 50 секунд на запуск: следующий cron-запуск подхватит остальное.

### C2. Функции — `lib/telegram.php`, раздел `// ---- Публикатор очереди ----`

```php
/** Посты всех пользователей со статусом queued и publish_at <= $now (и next_try_at <= $now), по publish_at. */
function outbox_due($now, $limit = 20): array { ... }

/**
 * Отправляет созревшие посты. $send(array $post, array $channel): array — ['url' => …] или исключение.
 * Подменяется в тестах. Возвращает ['sent' => N, 'failed' => M].
 */
function outbox_process_due($now, callable $send): array { ... }

/** Настоящая отправка: telegram_publish_prepared(канал, text, media). */
function outbox_send_post(array $post, array $channel): array { ... }
```

Порядок для каждого поста:
1. **Взять:** в `db_tx` перечитать строку; если статус уже не `queued` — пропустить (её взял другой процесс или
   отменили). Иначе `status = 'sending'`, `attempts + 1`, сохранить.
2. **Канал:** `telegram_connection($post['user_id'], $post['channel'])`. Канала нет (отключили) → сразу `failed` с
   ошибкой «Канал отключён».
3. **Отправить** `$send($post, $channel)`.
4. **Успех:** в `db_tx` удалить пост из `outbox`, записать в журнал опубликованных (`telegram_log_published` с `url`,
   `scheduled_for = publish_at`, `channel`, `channel_title`), затем удалить папку `data/outbox/<id>/`.
5. **Ошибка:** `attempts < 3` → обратно `queued`, `next_try_at = now + [60, 300, 900][attempts - 1]`, `error` — текст.
   `attempts >= 3` → `failed` + уведомление (C4).
   Ошибки, которые повтором не исправить (бот выгнан из канала, канал не найден, файл не найден, «Forbidden»,
   «chat not found»), — сразу `failed`, без повторов. Распознавай по тексту исключения из `telegram_bot_request`
   (посмотри, какой текст оно даёт, через `telegram_error_text`).
6. **Зависший `sending`:** пост в `sending` дольше 15 минут (процесс упал посреди отправки) — **не отправлять повторно**
   (пост мог уже выйти): `failed` с ошибкой «Отправка прервалась: проверьте канал — пост мог выйти. Если его нет —
   нажмите «Повторить»». Проверяй это в начале `outbox_process_due`.

Публикатор работает от имени разных пользователей: функции, которые зовут `app_user_id()`, вызывай после
`app_user_bind($post['user_id'])` или передавай `$uid` явно — проверь `telegram_log_published` и всё, что вызывается.

### C3. Страховка, если cron не настроен

В `tab_session_heartbeat` (`lib/runtime.php`, вызывается вкладкой раз в 5 секунд) добавь в конце: если есть созревшие
посты **этого** пользователя (дешёвый `SELECT 1 … LIMIT 1`) и замок `.publisher.lock` свободен — запустить
`tools/publisher.php` в фоне так же, как запускается парсер (`nohup … &`, без ожидания). Не чаще раза в 30 секунд на
пользователя (отметка в `kv`, ключ `publisher_kick:<uid>`). Отправку внутри запроса вкладки **не делай**: загрузка
видео занимает минуты.

### C4. Уведомление о провале

Если у пользователя есть `telegram_id` (вошёл через Telegram) и бот входа задан (`telegram_login_bot()`), бот входа
пишет ему в личку: «Пост в «<канал>» на <дата время> не вышел: <ошибка>. Повторить или удалить — в «Личном кабинете» →
«Соцсети» → «Очередь».» Ошибка отправки уведомления — только `error_log`, на пост не влияет.

## Часть D. Интерфейс

### D1. Расписание канала — «Соцсети» → у канала кнопка «Расписание»

Форма: семь строк (пн … вс), в каждой — поле со временами через запятую (`10:00, 14:00, 19:00`), кнопка «Как в пн»
копирует понедельник во все будни; поле «Случайный сдвиг, мин» (0–30); «Сохранить». Часовой пояс отправляется из
браузера автоматически, показывается подписью «Время по поясу Asia/Yekaterinburg». Новое действие
`channel_schedule_save` (POST, `channel`, `schedule`) и чтение расписания — в `channels_public()` (поле `schedule`).

### D2. Редактор поста — чип «Когда»

Сейчас: «сразу» или дата из `pickDateTime`. Добавь варианты (меню по клику, `bindMenu`):
- «Сразу»;
- «В ближайший слот» — только если у выбранного канала есть слоты; рядом подпись с временем слота, которое вернёт
  новое действие `telegram_next_slot` (GET, `channel`) → `{slot_at, publish_at}` или `{none: true}`;
- «Выбрать дату и время…» — как сейчас (`pickDateTime`);
- если у пользователя подключён аккаунт и выбрано время — переключатель «Через «Отложенные» Telegram (выйдет, даже
  если сайт выключен)» / «Через очередь Posta». По умолчанию — «Отложенные», если аккаунт есть.
`publishToTelegram` отправляет `mode` (`now` / `slot` / `queue` / `native`) и `scheduled_ts`.

### D3. Очередь — `loadTelegramQueue`

Для постов нашей очереди: время, канал, статус по-русски («ждёт», «отправляется», «не вышел: <ошибка>»), кнопки
«Отменить» (queued/failed), «Повторить» (failed), «Перенести» (queued: тот же выбор, что в D2). Посты через
«Отложенные» Telegram — как сейчас, с пометкой «в Отложенных Telegram».

Новые CSS-классы — только с префиксом `sched-`.

## Часть F. Проверка без настоящего Telegram

Создай `tools/test_schedule.php` (только CLI) и запусти **на копии проекта**:

```
T=$(mktemp -d) && cp -r bootstrap.php config.php config.local.php secret.key.php lib handlers tools "$T"/ \
  && mkdir "$T/data" "$T/users" "$T/media" && sqlite3 data/posta.sqlite ".backup $T/data/posta.sqlite" \
  && POSTA_MEDIA_CACHE_DIR="$T/media" php "$T/tools/test_schedule.php"; rm -rf "$T"
```

Отдельная папка медиа обязательна: без `POSTA_MEDIA_CACHE_DIR` тест работал бы с настоящими файлами в
`/var/lib/posta/media` (переменная появляется в `MEDIA_RECOVERY_PROMPT.md`, часть A — он делается раньше).

Скрипт печатает `OK …` / `FAIL …` и в конце число провалов. Отправку подменяй замыканием, которое запоминает вызовы и
по сценарию возвращает `['url' => 'https://t.me/x/1']` или бросает `RuntimeException`. Тестовые пользователи и
каналы — новые, созданные в скрипте (`channel_save` с выдуманным токеном). Медиа — маленькая PNG, созданная GD в
папке поста.

Сценарии:
1. **Слоты:** расписание пн–пт 10:00 и 19:00, `tz = Europe/Moscow`, jitter 0. От «понедельник 09:00 МСК» ближайший —
   пн 10:00; если на пн 10:00 уже стоит пост — пн 19:00; от «пятница 20:00» — следующий понедельник 10:00.
2. **Jitter:** jitter 10 → `publish_at` в пределах `slot_at ± 600`, а занятость определяется по `slot_at`.
3. **Пояс:** тот же слот в `Asia/Yekaterinburg` на 2 часа раньше по UTC, чем в Москве.
4. **Неверное расписание:** `25:00`, `10:7`, 25 слотов в день, неизвестный пояс → `InvalidArgumentException` (пояс —
   подмена на пояс сервера, не ошибка: выбери одно и проверь его).
5. **Отправка:** пост `queued` с `publish_at` в прошлом → `outbox_process_due` вызывает отправку 1 раз, пост удалён из
   `outbox`, в журнале опубликованных есть запись с `url`, папки `data/outbox/<id>` нет.
6. **Будущий пост** не отправляется.
7. **Повторы:** отправка бросает «Timeout» → `queued`, `attempts = 1`, `next_try_at` через 60 с; повторный вызов до
   `next_try_at` не отправляет; после трёх неудач — `failed`.
8. **Неисправимая ошибка** («Forbidden: bot was kicked») → сразу `failed` после первой попытки.
9. **Двойной запуск:** два вызова `outbox_process_due` подряд для одного созревшего поста → отправка 1 раз.
10. **Зависший `sending`** с отметкой 20 минут назад → `failed` без вызова отправки.
11. **Отмена `sending`** — отказ; отмена `queued` — пост и папка удалены.
12. **Канал отключён** до отправки → `failed` «Канал отключён», отправка не вызывалась.
13. В конце удали тестовых пользователей и папки.

Плюс `php -l` всех изменённых PHP и `node --check` изменённых JS.

## Отчёт пользователю

Перечисли изменённые файлы и шаги, которые нужны от него:
1. Добавить cron публикатора (строка из README, `sudo crontab -u www-data -e`).
2. «Соцсети» → канал → «Расписание»: задать слоты.
3. В редакторе выбрать «В ближайший слот» → «Через очередь Posta» и проверить, что тестовый пост вышел в своё
   время (`tail -f users/publisher.log`).

## Чего не делать

- Не менять путь через «Отложенные» Telegram (аккаунт, `tools/tg_user.py`).
- Не отправлять посты внутри веб-запроса вкладки — только фоновым публикатором.
- Не отправлять повторно пост, застрявший в `sending`.
- Не хранить файлы отложенных постов в `MEDIA_CACHE_DIR` и не в публичной папке.
- Не ставить задания в crontab и не публиковать в настоящие каналы при проверке.
