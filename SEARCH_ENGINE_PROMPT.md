# Задача: широкая воронка контента и настоящий поиск по запросу

Ты работаешь в Go-проекте `/var/www/html/posta` (Posta), ветка `go-rewrite`. Владелец: «контента находится мало, а его должно быть дохуя — много источников, много постов. И подбор должен работать как настоящий поисковик: не выбирать из распарсенного, а искать именно то, что нужно».

Задача большая. **Советуйся с Sonnet** (инструмент Agent, `model: "sonnet"`), когда:
- перед началом части B — покажи ему свой план интерфейса поисковых площадок и ранжирования, прими или обоснованно отклони замечания;
- баг не поддаётся после двух попыток (например, Двач в части A);
- в конце каждой части — попроси его проверить `git diff` на ошибки (корректность, гонки, утечки горутин, пропущенный украинский фильтр).
Советник только читает и отвечает; правки делаешь ты.

Перед началом:
- `git status` / `git diff`: в рабочей копии есть чужие незакоммиченные правки (`internal/posta/ytdlp.go`, `analysis.go`, `content.go`, `store.go`, `js/*.js` и др.). Не откатывай их и не включай в свои коммиты — добавляй в коммит только свои куски (`git add -p`).
- Номера строк ниже могли сдвинуться — ищи по именам функций.
- `SPREAD_AND_SEARCH_PROMPT.md` уже выполнен (коммиты 85e6840, 7b73597) — прочитай его как контекст, но не делай повторно.

## Правила проекта (обязательно)

- **Сборка и перезапуск:** `go build -o bin/posta ./cmd/posta && sudo systemctl restart posta`. Правки HTML/CSS/JS работают сразу.
- **Живую БД не трогай.** Тесты — `go test ./internal/posta/...` и dev-сервер: `POSTA_DEV=1`, порт 8097, dev Postgres на 55432 (см. `deploy/` и README). В dev-режиме парсеры не стартуют сами; вход для headless — `/dev-login?sid=…&to=…`.
- **Модели:** вызовы — через `u.LLM.Generate` с ролью, как в соседнем коде. Модель полного анализа не меняй на более слабую ради скорости. Платные модели выключены — всё должно работать на бесплатных и локальных. Не запускай платные прогоны.
- **Никаких `confirm`/`alert`** в JS: только `ask()` из `js/core.js`.
- **Настройки поведения** — строки `Tunables` в `internal/posta/tunables.go` (сами появляются в админке → «Управление»).
- **Украинский фильтр** (`UAItemBlocked`/`UASourceBlocked`) — на каждом новом пути поста.
- **Правило владельца не трогать:** один пост с источника в ленте темы (`per_source_pool`) и отдых источника после оценки (`source_cooldown_hours`). Контента должно стать больше за счёт **ширины** (больше источников), а не за счёт ослабления этого правила.
- Пиши как соседний код: короткие русские комментарии над функциями, `jx.M`, `u.Log(...)` на русском.

## Что выяснено (журнал прохода 2026-10-30 08:50, тема «Мемы»; перепроверять не нужно)

Журнал: `/var/lib/posta/data/users/<uid>/parser-v3.log`.

Воронка одного 40-минутного прохода:

```
Площадки: Telegram 385 постов (23 канала) · Двач 0 · 4chan 14 · YouTube 153 (12 каналов) · VK 0 — нет ключа · RSS 0
Горячие: 20 из 42
Кандидатов к проверке: 32. Устаревших: 4. Источники в ленте или на отдыхе: 55.
```

То есть **552 собранных поста → 32 кандидата**. Причины:

1. **Источников мало.** В каталоге темы «Мемы» — 5 опрашиваемых источников («Опрошено 5 из 5»), остальное — 30 находок автоподбора (`suggestion_sources_per_run = 30`, по одному посту с каждой). При правиле «один пост с источника + 24 ч отдыха» потолок ленты ≈ число источников ≈ 35 в сутки. Автодобавление находок выключено владельцем (`auto_add_score = 101`) — это не меняй.
2. **Находки читаются дорого, а берётся один пост.** `collectPostsByPlatform` вызывает `collectCatalogSource` для каждой находки (40 постов, превью роликов), чтобы взять `bestHeatPost`. Сбор занимает большую часть прохода.
3. **Двач даёт 0 постов на всех 9 досках**, хотя API отвечает. Проверено тестом: `Fetch2chJSON("b","")` → 212 тредов, у тредов есть медиа (`DvachPostMedia` находит). В живом проходе `ParseDvach` возвращает 0 и не пишет «тред не по теме» — значит пусто раньше гейта. Подозрения: `DvachJSONCached` кэширует ответ-ошибку как `{"threads": nil}` на 10 минут (`len(data) > 0` у JSON с ошибкой), или первые 8 тредов каталога (`DvachThreadsPerBoard`) — закреплённые/закрытые и после фильтра не остаётся ничего (фильтр стоит *до* среза — проверь), или запросы тредов режутся антиспамом 2ch при пачке подряд. Найди настоящую причину, не угадывай.
4. **Встроенный поиск по теме ищет мусор.** `PostSearchCandidates("Мемы")` дала запросы «image», «meme», «memes». Слово «image» — из `Profile.Keywords`, оно не описывает тему. Telegram по словам платный (работают только хэштеги), VK без ключа. Итог: «YouTube 9, Telegram 0, VK 0».
5. **В режиме запроса** (`QuerySearchCollect`) «поиск» — это одна формулировка (`ru[0]`) на площадку за проход, плюс **полный парсинг каталога** темы (`collectPostsByPlatform`) — именно «подбор из распарсенного». Потом всё снова проходит `buildCandidateQueue`, где `sourceBusy` выкидывает посты отдыхающих источников, а `hotShortlist` режет до `QueuePerSource = 2`. Сам поиск запускается только внутри прохода сборщика (до 40 мин, пауза `parser_cooldown` между проходами), а не по вводу запроса.
6. **Отсевы, которые не видно.** `candidateIsKnown` и дубли в `buildCandidateQueue` отбрасываются молча — в журнале нет счётчика, поэтому «552 → 42» не объясняется.
7. **Ролики длиннее 10 минут скачиваются, чтобы узнать, что они длинные** (34 раза за проход: «Ролик не скачан: ролик слишком длинный»). Длительность есть в метаданных списка yt-dlp — проверяй её до постановки в очередь превью.

## Часть A — широкая воронка (коммить отдельно)

1. **Двач.** Найди причину нуля (п. 3) и почини. Не кэшируй ответы без тредов. Добавь тест на фикстуре каталога, где первые треды закреплены.
2. **Находки — дёшево и все.** Для находок автоподбора не вызывай полный `collectCatalogSource`: читай одну страницу (Telegram — `FetchTelegramChannelPage`, YouTube — плоский список без превью роликов), выбирай `bestHeatPost`, видео превью ставь в очередь только для выбранного поста. Предел `suggestion_sources_per_run` подними по умолчанию до 100. Опрашивай находки параллельно (пул воркеров, тунабл `collect_workers`, по умолчанию 6, с уважением к FloodWait Telegram — посмотри, как это сделано в `telegram.go`).
3. **Каталог темы растёт сам.** Если в воронке прохода кандидатов меньше, чем `pool_target`, а автоподбор по теме был давно — запусти его в конце прохода (сейчас он запускается только при `added == 0`). Авторов постов, найденных поиском (часть B и встроенный поиск), отдавай в находки через `PostSearchSuggest` — так поиск расширяет каталог.
4. **Запросы встроенного поиска по теме.** В `PostSearchCandidates` выкидывай слова, которые не несут темы: латиница из одного общего слова («image», «video», «photo», «post», «content» — список в `config`), слова короче 4 букв. Для Telegram используй хэштеги (слова работают только за деньги): из ключевых слов темы и её подтем в виде `#мемы`, `#мем`, `#юмор`. Число запросов за проход — тунабл (`post_search_queries`, по умолчанию 6).
5. **Новые площадки для темы.** Встроенный поиск по теме ходит и в площадки части B (Rutube, 9GAG, Pikabu, Joyreactor, Mastodon по хэштегу) — по одному запросу на площадку за проход. Каждая площадка — отдельный тунабл-переключатель.
6. **Видимая воронка.** В итог сбора выводи все отсевы со счётчиками: «уже видели», «дубль», «устарело», «украинское», «источник занят», «срез очереди на источник», «срез шортлиста». Сумма должна сходиться с числом собранных постов.
7. **Ролики.** До постановки превью в очередь проверяй длительность из метаданных; длинные помечай сразу, без скачивания.

Проверка части A: прогон сборщика на dev-сервере по теме «Мемы» (или живой проход владельца, если dev не даёт сети к Telegram) — в журнале «Кандидатов к проверке» должно стать в разы больше 32, сумма отсевов сходится, Двач не ноль. Коммит: «Сборщик: широкая воронка — …».

## Часть B — поиск как поисковик

Цель: владелец вводит запрос («коты в коробках», «Тюмень пробки», «Шаман концерт») → система **ищет** посты про это по площадкам, а не фильтрует каталог. Результаты появляются в ленте за минуту-две, дальше подгружаются ещё.

1. **Интерфейс площадки.** Новый файл `internal/posta/search_engine.go`:
   ```go
   // SearchBackend — одна поисковая площадка.
   type SearchBackend struct {
       Name     string                                              // «Rutube», «9GAG», …
       Platform string                                              // для source_key и учёта долей
       Tunable  string                                              // переключатель в админке
       Search   func(u *U, q string, page int) ([]jx.M, bool, error) // посты страницы; bool — есть ли ещё
   }
   ```
   Существующие поиски (Telegram хэштеги и каналы, YouTube, VK, TikTok, Google/Bing News, vc/dtf) оберни в этот интерфейс; новые — Rutube, 9GAG, Pikabu, Joyreactor, Lemmy, Mastodon. Каждый пост — в обычном формате пула (`url`, `image`, `images`, `video`, `text`, `posted_at`, `source`, `source_key`, `source_url`, `engagement`, `found_by`). Парсеры HTML/JSON — чистые функции с тестами на фикстурах в `tools/fixtures/` (сохрани реальные ответы, как лежат `vc_search.json`, `gnews_rss.xml`).
2. **Параллельный опрос.** Все включённые площадки × формулировки плана опрашиваются параллельно (errgroup или пул воркеров), у каждой свой таймаут (тунабл `query_search_seconds` — общий бюджет), паника одной площадки не роняет остальные. Кэш ответа площадки по (площадка, запрос, страница) — 1 час, как `postSearchCached`.
3. **Формулировки.** `QuerySearchPlan` оставь, но используй **все** формулировки плана, а не `ru[0]`. Страницы: курсор по (площадка, формулировка) хранится в kv `query_search:cursor:<key>`; следующий проход берёт следующую страницу, пока площадка говорит «есть ещё».
4. **Без каталога по умолчанию.** В режиме запроса не вызывай `collectPostsByPlatform`. Каталог участвует дёшево: ищи по словам запроса в уже закэшированных постах источников (`SourcePollCacheKey`), без новых запросов к сети.
5. **Ранжирование, а не фильтр.**
   - лексика: `queryLex` замени на счёт в духе BM25 по `title + text + hashtags` с основами слов (как `queryWordHit`), веса: обязательные слова > формулировки > хэштеги;
   - дальше **текстовый реранк** моделью: верхние ~60 по лексике одним батчем (как `AnalyzeTextBatch`, роль быстрой/бесплатной модели) → `query_match` 0–100; кэш по (запрос, url);
   - итог: `query_match` × свежесть × горячесть (`hotRelativeHeat`); дубли — оставляй раньше опубликованный; один пост с источника; доля площадки ≤ `querySearchPlatformCap`.
   Полный анализ с картинкой — только для верхних результатов, как сейчас (он и так ставит `relevance ≤ query_match`).
6. **Отдых источника в режиме запроса не действует.** Владелец сам попросил этот запрос: `sourceBusy` в режиме запроса проверяет только «уже есть в ленте», не 24-часовой отдых. Правило «один пост с источника» остаётся.
7. **Запуск по вводу.** `save_query` (`internal/web/h_content.go`) с непустым запросом запускает проход сразу (`StartParser(force)`), без `parser_cooldown`; текущий проход по старому запросу останавливается (там уже есть проверка смены ключа — убедись, что она срабатывает быстро, а не после пачки). В консоль сайта — строка по каждой площадке: «Rutube: 18 · 9GAG: 30 · Pikabu: 0 (ошибка 403) …».
8. **Источники из поиска.** Авторы найденных постов, прошедших анализ, — в находки (`PostSearchSuggest`), чтобы поиск расширял каталог темы.
9. **CLI для проверки.** `posta search-test "<запрос>" [тема]` (в `cmd/posta`, рядом с `discovery-run`): прогоняет план, все площадки, ранжирование без полного анализа и без записи в пул; печатает по площадкам число постов и топ-20 с `query_match`. Работает против dev-БД.

Проверка части B: `posta search-test` по трём запросам — «коты в коробках», «Тюмень пробки», «Шаман концерт» — в топ-20 каждого не меньше 12 постов действительно про запрос и не меньше 5 разных площадок. Покажи вывод в отчёте. `go test ./internal/posta/...` зелёный. Коммит: «Поиск по запросу: площадки параллельно, страницы, ранжирование».
