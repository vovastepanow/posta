# Задача: частная тема («Абсурдный юмор») ищет то же, что общая («Мемы и юмор») — научить подбор отличать подтемы

Ты работаешь в проекте `/var/www/html/posta` (Posta). Владелец выбрал тему «Абсурдный юмор» (`humor.absurd`), а получает обычные мемы
с понятной шуткой — ровно то же, что в «Мемы и юмор». Нужно, чтобы частная тема пропускала только свои записи, а обычный юмор отсекала.
Решение делай **общим для всех частных тем** (чёрный юмор, фейлы, ниши бизнеса…), проверяй на «Абсурдном юморе» и «Чёрном юморе».

Ничего не коммить. Модель анализа не менять: только `SMART_MODEL` (qwen3.5-vision 9B), не подменять на 2B ради скорости.
Видеокарта — 1060 3 ГБ, большая модель идёт почти вся на CPU: **новых вызовов умной модели на запись не добавлять** — только заменять существующие.

## 1. Что выяснено (2026-10-23, БД `data/posta.sqlite` только на чтение, перепроверять не нужно)

Запись темы: `topics.id = 't8e6b3d4b'`, `key humor.absurd`, `about` «Бессмысленное смешное без понятной шутки.», родитель «Мемы и юмор».
История по теме: 53 жалобы, 23 дизлайка, 23 лайка, 16 «не знаю». Последние показанные (23.10) — анимешник и merge-конфликт, бабушка и Rust от Opus,
Прохор Шаляпин в видеозвонке, «парни когда что угодно» — обычные мемы, у всех `relevance` 85–92 и **у всех метка `humor.absurd`**.

Пять причин, все подтверждены кодом:

1. **Якоря `relevance` написаны под юмор вообще** (`lib/ai.php:406`, `content_analysis_prompt`): «61–85 явно по теме: видна шутка в надписи;
   86–100 шутка очевидна и узнаваема». Для абсурда это наоборот: обычная понятная шутка получает 85+. Критерии частной темы идут лишь
   подсказкой в конце (`topic_profile_hint`), и модель им не следует.
2. **Проверка «есть ли шутка» душит абсурд** (`lib/ai.php:427–442` `joke_yes_score`/`joke_present`, применяется в `:469` для всех `topic_is_humor`,
   включая все `humor.*`; ещё `:649` — `$joke === ''` режет оценку). Вопрос «есть ли шутка, понятная без додумывания» отбирает ровно обычные мемы,
   а настоящий абсурд («без понятной шутки» по определению темы) получает потолок `JOKE_NO_CAP = 40`.
3. **Метка темы подтверждает сама себя.** `quality_tag_penalty` (`lib/quality.php:41`) снижает оценку на 15, если среди меток записи нет ключа
   частной темы. Но в промпте модель видит тему подбора — и ставит `humor.absurd` всему подряд. Штраф не срабатывает никогда.
4. **Быстрый отсев пропускает всё.** Вопрос профиля для 2B (`quick_yes_no_payload`, `lib/ai.php:531`):
   «Это абсурдная ситуация, где действие или объект явно противоречат логике или реальности без явного контекстного объяснения?» — слишком
   абстрактный: средняя быстрая оценка по теме 86 (у «Мемов и юмора» 54), 70% записей — 90–100.
5. **Источники — чужие.** У темы один свой канал (`shitposthumanism`), меньше `TOPIC_PARENT_FALLBACK_MIN = 3` (`lib/topics.php:7`, `:195`),
   поэтому берутся все каналы «Мемов и юмора». Больше всего записей темы — из `bankrollo`, `ithumor`, `current_memes`, `prikoly_humor_memy` (обычные мемы),
   настоящие шитпост-каналы в каталоге есть: `experimentaldivashitposting`, `shitpostingtg`, `shitposthumanism`.

Ещё: профиль темы (`topic_profile_build`, `lib/topics.php:481`) строится без знания соседних подтем — `exclude` не говорит «обычные мемы с понятной шуткой — это не сюда».

## 2. Что сделать

### A. Выбор среди соседей вместо «есть ли шутка» (главное)
Для частной темы (у записи темы есть родитель и у родителя ≥ 2 детей) замени отдельный вызов `joke_yes_score` на **вопрос-выбор среди соседних тем**,
который **не знает, какую тему ищет пользователь** (иначе модель подыгрывает, как с метками):

- Варианты: все дети родителя (название + `about`) + сам родитель как «обычное / ничего из перечисленного» + «не по теме вообще».
  Порядок вариантов — фиксированный (по порядку в дереве), буквы A, B, C… Пример для юмора:
  «A — Шутки и анекдоты: смешной текст или подпись с понятной шуткой; B — Неудачи: …; C — Абсурдный юмор: бессмысленное, сюрреалистичное, шитпост, смешно без понятной шутки; D — Чёрный юмор: …; E — Прочий юмор; F — не юмор».
- Тот же вызов умной модели с картинкой (или листом раскадровки, как сейчас идёт `joke_yes_score`), `num_predict` 2–4, `temperature 0`, `logprobs` —
  берём вероятность буквы искомой темы и максимальную из остальных (функция `yes_probability_score` — образец разбора logprobs). Без logprobs — по букве ответа.
- Правило: искомая тема выиграла (её вероятность — наибольшая) → оценку не трогаем; проиграла соседу → `relevance = min(relevance, SUBTOPIC_LOST_CAP)` (новая константа в `config.php`, 40);
  ответ «не по теме» → `min(relevance, 20)`. Нет ответа → как сейчас при отсутствии ответа на шутку.
- Сохрани результат в записи анализа (`subtopic`: ключ выигравшей темы, `subtopic_p`: вероятность искомой) — пригодится в отчёте и в кэше.
- Для **общей** темы «Мемы и юмор» и `humor.jokes` / `humor.other` / `humor.fails` проверка «есть ли шутка» остаётся как есть — там она полезна.
  Для `humor.absurd` её не делать совсем (и правило `:649` про пустой `joke` для неё не применять) — вместо неё работает выбор.
- Проверь, что текстовая ветка (`analyze_text_batch`, посты без картинки, `judge = text`) тоже получает выбор — текстом, без картинки, если она сейчас делает отдельные вызовы; если отдельных вызовов там нет — не добавляй, просто опиши в отчёте.

### B. Якоря relevance — под тему, а не под юмор
В `content_analysis_prompt`: якоря «шутка видна / шутка очевидна» оставь только для тем, где шутка и есть суть (общий юмор, шутки, прочий юмор).
Для частной темы — общие якоря: «0–30 не про тему; 31–60 подходит под общую тему «{родитель}», но признаков именно «{тема}» нет; 61–85 явно «{тема}»;
86–100 яркий пример именно «{тема}»». И одна строка контраста: «Обычная запись темы «{родитель}» без признаков «{тема}» — не выше 50».

### C. Метка темы не подтверждает сама себя
`quality_tag_penalty`: для частной темы с результатом выбора (A) штраф решает выбор, а не метки. Где выбора нет (текстовая ветка без вызова) — оставь как есть.

### D. Профиль темы знает соседей
`topic_profile_build`: в промпт добавь родителя и соседей с их `about`: «Соседние темы (НЕ эта): …». `exclude` обязан назвать, чем тема отличается от
родителя и ближайшего соседа. Вопрос для быстрой модели — конкретный, про видимое, с примерами (как «Это картинка с мотоциклом?»), без абстракций
«противоречит логике без контекстного объяснения». Подними `TOPIC_PROFILE_VERSION`, чтобы профили перестроились; быстрые оценки темы при смене вопроса
и так сбрасываются (`topic_profile_ensure`).

### E. Описания подтем юмора
`lib/taxonomy/humor.php` (ключи НЕ менять): сделай `about` каждой подтемы различающим — что входит и чем отличается от соседей, 1–2 предложения.
Для `humor.absurd`: сюрреалистичное и бессмысленное, шитпост, проклятые картинки, странный монтаж, смешно без понятной шутки и панчлайна;
обычный мем с понятной шуткой или отсылкой — не сюда. Алиасы добавь: «сюр», «сюрреалистичный юмор», «шитпостинг», «проклятые картинки», «мемы без смысла».
Проверь, как дерево из `lib/taxonomy` попадает в таблицу `topics` (`topic_tree_seed`, `lib/topics.php:251`) — обновится ли `about` у уже существующей
записи темы; если нет — обнови через существующий путь (CLI в `tools/cli.php`), не правь БД руками.

### F. Источники частной темы
1. Каналы, где запись по частной теме реально проходит в пул (не быстрая оценка — она завышена, а итог полного анализа + лайки/жалобы), должны идти
   первыми; каналы родителя, у которых по этой теме за последние N записей почти никто не прошёл (порог — константой), — в конец/пропуск по этой теме.
   Посмотри, что уже есть: `source_pass_rates`, `combined_source_rates`, `user_rates_for_run` (`lib/parser.php:108`) — скорее всего достаточно
   считать проход по итогу анализа, а не по `screened_cache.score`. Не делай новую таблицу, если хватает существующих.
2. Поиск источников для темы с < 3 своих каналов запускай, как он уже устроен (`lib/discovery.php`, поиск по аккаунту Telegram — веб-поиск сервер не пускает).
   Запросы профиля после D должны стать вроде «шитпост», «абсурд», «сюр», «проклятые картинки», «мемы без смысла». Названия каналов врут
   («абсурд виктора» — селфи и котики, 9 жалоб): канал привязывать к теме только после проверки его постов, как это уже делает discovery.

### G. Кэши
После правок оценки по частным темам юмора в `screened_cache` и `analysis_cache` устарели. Сбрось их **только для «Абсурдного юмора» и «Чёрного юмора»**
(посмотри, как устроен `analysis_cache_key` — входит ли тема). Остальные темы не трогать. Делай через PHP-функции проекта / CLI, не во время работы парсера
(проверь `parser_runtime`).

## 3. Проверка

- **Не открывай страницу приложения как новый пользователь** (headless-загрузка создаёт пользователя и запускает парсер). Проверяй из CLI.
- Тестовый набор без ручной разметки: по 20 записей с картинками
  — «абсурд»: последние посты `experimentaldivashitposting`, `shitpostingtg`, `shitposthumanism`;
  — «обычный юмор»: `ithumor`, `current_memes`, `prikoly_humor_memy`;
  плюс 15 записей из жалоб по теме (`history_items`, `collection='complaints'`, тема «Абсурдный юмор») — если медиа ещё доступно.
  Прогони полный анализ по теме «Абсурдный юмор» (`tools/cli.php` — посмотри, есть ли команда оценки одной записи; нет — добавь маленькую, без записи в пул).
  Цель: из «обычного юмора» в пул (оценка ≥ `RELEVANCE_THRESHOLD`) проходит ≤ 20%, из «абсурда» — ≥ 50%, из жалоб — ≤ 15%. Таблицу «до/после» — в отчёт.
  Время одной записи до и после (не должно вырасти больше чем на 10%: вызов заменяем, а не добавляем).
- То же на 10 + 10 записях для «Чёрного юмора» (обычный юмор не должен проходить).
- Регресс: 20 записей из лайков «Мемы и юмор» по теме «Мемы и юмор» — проходят не хуже, чем до правок.
- `php -l` на каждый изменённый файл; `tools/quality_report.php` — запускается без ошибок.

## 4. Отчёт
Коротко, по-русски: что поменял (файлы, функции), таблицы проверки, примеры описаний записей, которые теперь отсекаются и которые проходят,
что не получилось. Не обещай, что «теперь идеально»: частные темы зависят ещё и от того, есть ли под них каналы.
