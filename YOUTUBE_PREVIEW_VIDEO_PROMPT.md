# Задача: шортсы YouTube очень долго грузятся в превью кандидатов-источников

Ты работаешь в PHP-проекте `/var/www/html/posta` (Posta). Вкладка «Источники» показывает кандидата в источники с мозаикой примерных постов
(`handlers/sources.php`: `handle_suggest_sources` → `build_source_preview`; интерфейс `js/sources.js`, `js/post-view.js`, `js/post-adapters.js`,
ожидание ролика — `js/video-pending.js`). Владелец: **«очень долго грузятся видео с ютуба, а именно шортсы»**. Обычные ролики (`/watch?v=`) не трогай —
у них файла нет вообще, это отдельная задача.

## Как сейчас устроено (2026-10-24, прочитано в коде; цифры времени НЕ замерялись)

1. Шорт в превью получает `video_via = 'ytdlp'`, `video_page = https://www.youtube.com/shorts/<id>` (`lib/rss.php` ~стр. 173, `lib/youtube.php`: `youtube_post`).
   Первые `VIDEO_PREVIEW_FIRST` (3) ролика превью встают в очередь сами, остальные — по кнопке (`handle_video_fetch` → `video_fetch_enqueue`, `lib/ytdlp.php`).
2. Очередь одна на всё: `kv ytdlp_queue` — и превью, и ролики пула контента (TikTok, шортсы, большие видео Telegram). Превью по кнопке ставится первым (`$front`),
   авто-превью и пул — в хвост.
3. Воркер `tools/ytdlp_worker.php` — **один на сервер** (`.worker.lock`), задачи **строго по одной**, и `ytdlp_download` держит ещё `.download.lock`
   («не больше одного скачивания на сервер»). Запускается `ytdlp_kick_worker()` через `proc_open`, без cron.
4. Одно скачивание шорта (`ytdlp_download`, `lib/ytdlp.php` ~стр. 145):
   - запуск `python3 -I tools/bin/yt-dlp` (zipapp — каждый раз заново распаковка/импорт);
   - **первая попытка без JS** (`$js = !$youtube` → для YouTube `false`), при неудаче — **вторая, полная, с Node** (`tools/bin/node-quiet`, Node `--jitless`
     из‑за ограничений apache2, комментарий говорит «~5 с»). Если первая попытка у шортсов теперь стабильно падает, каждый ролик платит две попытки;
   - формат `bv*[vcodec^=avc1][height<=1280]+ba[ext=m4a]/b[ext=mp4]` — видео и звук отдельно, потом склейка ffmpeg;
   - после — `ytdlp_codec` (ffprobe) и при не‑H.264 перекодирование `ytdlp_h264` (libx264, может идти десятки секунд);
   - `cache_downloaded_video`.
5. Браузер опрашивает `video_status` (`js/video-pending.js`: `POLL_MS` / `POLL_ACTIVE_MS`).

Подозреваемые причины медленности (проверить, а не верить): (а) две попытки yt-dlp на каждый шорт; (б) превью ждёт в общей очереди за роликами пула
и за другими превью — всё последовательно; (в) перекодирование, если формат avc1 не нашёлся; (г) старт воркера/интервал опроса; (д) сама сеть/YouTube.

## Ограничения

- **Не открывай приложение в headless-браузере с чистым профилем**: новая загрузка = новый пользователь + парсер, который не остановить.
- Живую базу `data/posta.sqlite` не меняй (владелец недавно её чистил) — для опытов копия в scratch-папку. Чтение — `sqlite3 -readonly`.
- Воркер работает под apache2 с его ограничениями (Node без JIT, Chrome без песочницы). Замеры запускай так же: `systemd-run --user --wait --pipe ...`,
  иначе цифры из твоей оболочки будут не те.
- Не ломай TikTok, большие видео Telegram (`tgu`) и очередь пула. Не коммить.

## Шаг 1. Замерить (обязательно до правок)

Возьми 3–5 реальных шортсов из превью кандидатов YouTube (`source_suggestions`, лента `youtube.com/feeds/videos.xml?...` / `playlist_id=UUSH...`).
Для каждого замерь по стадиям, во временную папку:

1. yt-dlp **без** `--js-runtimes` — время и успех/ошибка (stderr);
2. yt-dlp **с** `--js-runtimes node:tools/bin/node-quiet` — время и успех;
3. какой формат реально выбран (`--print format_id,vcodec,height`), был ли нужен перекод (ffprobe кодек);
4. размер файла.

Те же аргументы, что в `ytdlp_run`/`ytdlp_download` (`--ignore-config --no-warnings --cache-dir <YTDLP_CACHE_DIR> --socket-timeout 15 -f <формат> --merge-output-format mp4 ...`).
Отдельно оцени, сколько в среднем лежит задач в `ytdlp_queue` и чьих (превью `preview:*` или пул), — по снимкам `kv` несколько раз с интервалом,
и сколько ждёт превью, пока до него дойдёт очередь.

Добавь в `ytdlp_run_job` строку в журнал (`cli_echo`) с временем каждой стадии и номером попытки — это остаётся и после задачи, пригодится.

## Шаг 2. Ускорить — по результатам замеров

Делай то, что замеры подтвердили; что не подтвердилось — не трогай и напиши почему. Возможные правки:

1. **Попытка без JS стабильно не работает для шортсов** → для YouTube сразу запускать с Node (убрать лишний проход). Если работает и быстрее — оставить порядок.
   Можно запоминать в `kv` на час, какой режим сработал последним, и начинать с него.
2. **Превью ждёт за пулом** → задачи превью (`video_is_preview_key`) всегда брать раньше задач пула (`ytdlp_next_job` / `ytdlp_next_job_within`),
   включая авто-первые 3. Пул контента не срочный, человек в превью ждёт прямо сейчас.
3. **Строго одно скачивание на сервер** → разрешить 2 параллельных скачивания yt-dlp (например, второй слот только для превью), если замеры показывают,
   что сервер (слабый CPU, GTX 1060 занята моделями) это выдерживает: смотри загрузку CPU во время скачивания. Лимит на сайт (`VIDEO_PREVIEW_LIMITS`) сохранить.
4. **Перекод** → если находится только VP9/AV1, попробовать `-S vcodec:h264,res:720` / ограничить `height<=720` для шортсов превью, чтобы avc1 находился
   и ffmpeg только склеивал.
5. **Опрос в браузере** → если `POLL_MS` большой, а ролик готов раньше, — уменьшить для превью (но не чаще раза в 1–1,5 с).
