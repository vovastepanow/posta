# Задача: жалобы «ошибка подбора» должны учить модель

Ты работаешь в PHP-проекте `/var/www/html/postmaker`. Парсер подбирает картинки и видео по теме. Сначала быстрая модель
(qwen3-vl 2B) отвечает «да/нет» по вопросу из профиля темы, потом умная модель (qwen3.5-vision 9B) делает полный анализ
и ставит «по теме» (relevance) от 0 до 100. В пул попадает запись с relevance ≥ 61.

Пользователь жалуется на записи кнопкой 🚩 → «ошибка подбора» (в истории это коллекция `complaints`,
`complaint_reason = 'match_error'`). Жалоб уже 111, а толку нет: модель снова ставит 75–85% скриншоту биржи в теме
«Абсурдный юмор».

**Почему так.** Сейчас жалоба влияет только на две вещи:
1. Рейтинг источника (`source_feedback_stats` / `combined_source_rates` в `lib/sources.php`). Источник отключается лишь
   после 8 голосов с долей хороших меньше 0,2.
2. Примеры вкуса (`history_taste_texts` в `lib/ai.php`). Но они выключены (`PERSONAL_TASTE_ENABLED = false`), поэтому
   модель жалоб не видит вообще.

Нужно, чтобы жалобы доходили до обеих моделей: до умной — как примеры, до быстрой — через профиль темы.

Делай части по порядку: A → B → C → D. Не начинай следующую, пока проверка предыдущей не прошла.

## Общие правила

- **Сначала прочитай целиком:** `lib/topics.php` (разделы «Профиль темы» и функции `topic_same`, `topic_lookup`,
  `topic_save`), `lib/ai.php` (`content_analysis_prompt`, `history_taste_texts`, `analyze_content_with_vision`),
  `lib/db_access.php` (`history_load`, `screened_cache_load`), `lib/parser.php` (`analyze_candidate`, `run_collector`),
  `js/content.js` (функция `vote`), `config.php`.
- **Меняй только `lib/topics.php`, `lib/ai.php`, `js/content.js`.** Другая сессия параллельно правит `lib/parser.php`,
  `lib/db.php`, `lib/db_access.php`, `lib/content.php`, `tools/cli.php` (распознавание повторов). Эти файлы только читай.
- **Не делай git commit.** Пользователь проверит изменения сам.
- **Пиши в стиле проекта.** Короткие функции, комментарии по-русски, без классов и лишних абстракций.
- **Не запускай парсер и модели** (`cron_parser.php`, Ollama, `topic_profile_build`). Они идут на слабой видеокарте и
  занимают минуты. Живую проверку сделает пользователь.
- **Не открывай сайт в безголовом браузере и не дёргай curl'ом** `get_current_item`, `tab_open`, `refresh_content`.
  Каждый заход без куки пользователя создаёт нового пользователя и запускает фоновый парсер, который нельзя остановить.
- **Перед любым запуском, который пишет в базу, сделай копию:**
  `sqlite3 data/postmaker.sqlite ".backup data/postmaker.sqlite.bak-complaints"`.

## Факты, которые нужно знать

- Настоящий пользователь — `b34cfe131b9ddea519d4cbd42c831fb5`, его тема сейчас «Абсурдный юмор». В его истории 13 жалоб
  по этой теме и около 100 по другим.
- В записи истории тема лежит в поле `topic`. Это строка как при подборе: название темы или составная «первая + вторая».
  Сравнивай её с темой только через `topic_same()`, не через `===`.
- Текст для примера — поле `description` записи: это описание от той же умной модели.
- Профиль темы общий для всех пользователей. Он хранится в теме (`$e['profile']`) и чистится функцией
  `topic_profile_clean()`. **Поля, которых нет в её списке, молча пропадают при сохранении.**
- Быстрые оценки хранятся в SQLite, в таблице `screened_cache` (колонки `url`, `topic`, `source`, `score`, `at`).
  JSON-файла `SCREENED_CACHE_FILE` больше нет.

## Часть A. Сбор жалоб

В `lib/topics.php`, после раздела «Профиль темы», добавь раздел `// ---- Жалобы «ошибка подбора» учат тему ----`:

```php
const TOPIC_COMPLAINT_EXAMPLES = 8;   // сколько последних жалоб видит полный анализ
const TOPIC_COMPLAINT_STEP = 5;       // через сколько новых жалоб по теме профиль переписывается

/** Жалобы «ошибка подбора» на записи темы (с непустым описанием), старые первыми. $history — одного пользователя; null — всех. */
function topic_complaints($topic, ?array $history = null) { ... }

/** Описания последних $limit жалоб, каждое обрезано до TASTE_EXAMPLE_CHARS символов. */
function topic_complaint_texts(array $records, $limit) { ... }
```

- `topic_complaints`: если `$history === null`, обойди `user_ids()` и для каждого возьми `history_load($uid)`. Бери
  записи из `$h['complaints']`, где `complaint_reason === 'match_error'`, `topic_same((string)$r['topic'], $topic)` и
  `trim(description) !== ''`. Отсортируй по `timestamp` по возрастанию.
- `topic_complaint_texts`: последние `$limit` записей → `mb_substr(trim(description), 0, TASTE_EXAMPLE_CHARS)`.

**Проверка A:**
```
php -l lib/topics.php
php -r 'require "bootstrap.php"; app_user_bind("b34cfe131b9ddea519d4cbd42c831fb5");
  echo "моих по теме: ", count(topic_complaints("Абсурдный юмор", history_load())), ", всех: ", count(topic_complaints("Абсурдный юмор")), "\n";
  print_r(topic_complaint_texts(topic_complaints("Абсурдный юмор", history_load()), 3));' 2>&1 | grep -v JIT
```
Ожидается 13 своих (плюс-минус несколько, если пользователь успел ещё пожаловаться) и три понятных описания.

## Часть B. Полный анализ видит жалобы

В `content_analysis_prompt` (`lib/ai.php`) сразу после строки про `relevance` (перед строкой про `rating`) вставь блок.
Он появляется, только если жалобы есть:

```
Пользователь уже пожаловался, что эти записи НЕ подходят под тему подборки, хотя их пропустили.
Запись, похожая на них по смыслу или виду, получает relevance не выше 30:
["описание 1", "описание 2", …]
```

- Жалобы бери из `$history` — это история текущего пользователя, она уже передаётся в функцию:
  `topic_complaint_texts(topic_complaints($topic, $history), TOPIC_COMPLAINT_EXAMPLES)`.
- Список выводи через `json_encode(..., JSON_UNESCAPED_UNICODE)`, как в блоке примеров вкуса ниже.
- **Не трогай остальной промпт.** Блок «Запись:» должен остаться в конце: начало промпта одинаково для всех записей, и
  Ollama переиспользует его кэш.
- Учти, что `$history` бывает пустым массивом или `empty_history()` («Тест ИИ», демо). Тогда блока просто нет.

**Проверка B:**
```
php -l lib/ai.php
php -r 'require "bootstrap.php"; app_user_bind("b34cfe131b9ddea519d4cbd42c831fb5");
  $p = content_analysis_prompt("Абсурдный юмор", "", history_load(), null);
  echo mb_substr($p, mb_strpos($p, "пожаловался") - 20, 700), "\n---\nвсего символов: ", mb_strlen($p), "\n";
  echo str_contains(content_analysis_prompt("Абсурдный юмор", "", empty_history(), null), "пожаловался") ? "ОШИБКА: блок без жалоб\n" : "без жалоб блока нет — верно\n";' 2>&1 | grep -v JIT
```
Весь промпт должен быть не длиннее ~5500 символов: контекст модели 4096 токенов, ещё нужны картинка и ответ.

## Часть C. Профиль темы учитывает жалобы

Так жалобы дойдут до быстрой модели: её вопрос «да/нет» и подсказка «Не подходит: …» берутся из профиля темы.

### C1. Новое поле профиля

В `topic_profile_clean` добавь `'complaints' => (int)($p['complaints'] ?? 0)`: по скольким жалобам составлен профиль.
Без этого поле пропадёт при сохранении.

### C2. Промпт профиля

У `topic_profile_build(array $e)` добавь второй параметр `array $complaints = []` (тексты из `topic_complaint_texts`).
Если он не пустой, добавь в промпт перед строкой «Ответь только JSON» абзац:

```
Пользователи пожаловались, что эти записи НЕ подходят под тему, хотя их пропустили: [...].
Пойми, что в них общего, и опиши это в exclude. criteria и question сделай строже, чтобы такие записи не проходили.
```

В возвращаемый профиль запиши `'complaints' => <сколько всего жалоб было по теме>`. Передай это число третьим параметром
или посчитай снаружи и допиши к результату в `topic_profile_ensure` — как тебе проще, лишь бы поле сохранялось.

### C3. Когда переписывать

В `topic_profile_ensure`:
- посчитай `$all = topic_complaints($e['title'])` (все пользователи);
- сейчас профиль возвращается сразу, если он актуален. Добавь условие: **не** возвращать сразу, если
  `count($all) >= ($p['complaints'] ?? 0) + TOPIC_COMPLAINT_STEP` и с прошлого профиля прошло больше 10 минут
  (`time() - $p['at'] > 600`). Пауза нужна, чтобы при сбое модели не переписывать профиль каждый запуск;
- вызывай `topic_profile_build($e, topic_complaint_texts($all, TOPIC_COMPLAINT_EXAMPLES))`;
- после сохранения напиши в журнал через `cli_echo`, если профиль обновлён по жалобам:
  `Профиль темы «…» уточнён по N жалобам. Не подходит: <exclude>`.

### C4. Почини сброс быстрых оценок

В `topic_profile_ensure` есть блок: при смене вопроса стираются прежние быстрые оценки темы. Он чистит старый JSON-файл
через `load_data(SCREENED_CACHE_FILE)`, а оценки теперь в SQLite, так что блок ничего не делает. Замени его: в
`db_tx(...)` пройди по `screened_cache_load()` и для строк, где `topic_same($r['topic'], $e['title'])`, выполни
`db_exec('DELETE FROM screened_cache WHERE url = ?', [$r['url']])`. Это важно: после уточнения профиля картинки темы должны
оцениваться заново, по новому вопросу.

**Проверка C** (без запуска модели):
```
php -l lib/topics.php
php -r 'require "bootstrap.php";
  $e = topic_lookup("Абсурдный юмор"); $p = $e["profile"];
  echo "жалоб всего: ", count(topic_complaints("Абсурдный юмор")), ", в профиле учтено: ", $p["complaints"] ?? 0, ", шаг: ", TOPIC_COMPLAINT_STEP, "\n";
  echo "complaints переживает чистку: ", topic_profile_clean($p + ["complaints" => 7])["complaints"], "\n";' 2>&1 | grep -v JIT
```
Ожидается: жалоб ≥ шага, в профиле учтено 0. Значит, при следующем поиске профиль перепишется. Вторая строка — `7`.

Промпт профиля проверь глазами, не вызывая модель: временно выведи его через `echo` в отдельном одноразовом скрипте в
`/tmp` (скопируй сборку строки) и убери скрипт после проверки. В `lib/topics.php` отладочного вывода остаться не должно.

## Часть D. Пользователь видит, что жалоба учтена

В `js/content.js`, в функции `vote`, после успешного `await api('vote', …)` и до `loadCurrentItem()`: если
`type === 'wrong' && details.reason === 'match_error'`, выведи в журнал через `log(...)`:

```
🚩 Жалоба учтена: ИИ увидит эту запись как пример «не по теме», источник теряет рейтинг, а каждые 5 жалоб уточняют профиль темы.
```

Больше в `vote` ничего не меняй. Сначала прочитай файл: его недавно правили, найди функцию по имени, не по номеру строки.

**Проверка D:**
```
node --input-type=module --check < js/content.js && echo ok
```
**Обязательно `--input-type=module`.** Простой `node --check` пропускает ошибки в модулях. Прошлый раз из-за этого лишняя
скобка в `js/content.js` уронила весь сайт.
