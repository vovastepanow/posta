## Правила проекта (обязательно)

- **Сборка и перезапуск:** `go build -o bin/posta ./cmd/posta && sudo systemctl restart posta`. HTML/CSS/JS работают сразу, без сборки.
- **Живую БД руками не трогай.** Тесты — `go test ./internal/...`, dev-сервер `POSTA_DEV=1` на 8097.
- **Headless-проверка:** свежая загрузка страницы создаёт пользователя и запускает парсер (см. память проекта). UI проверяй на dev-сервере с сессией из hex-строки. В headless Chrome `requestAnimationFrame` ненадёжен, поэтому город на скриншоте может оказаться плоским — это не баг. WebGL в headless: `--use-angle=swiftshader --enable-unsafe-swiftshader`.
- **Никаких `confirm`/`alert`** в JS: только `ask()` из `js/core.js`.
- **Внешних CDN в приложении нет.** Three.js положи локально (см. часть A).
- Пиши как соседний код: короткие русские комментарии, `jx.M`, `u.Log(...)` на русском.

## Как сейчас (прочитано 2026-10-30)

- `studio.html` — корневая страница. Три колонки: `.side` (меню), `.main`, `.panel` (быстрые действия и последние события). Стили — `css/shell.css` (токены) и `css/studio.css`.
- `js/studio.js` (≈290 строк) импортирует `createGlobe` из `js/studio-globe.js`, земля лежит в `js/studio-land.js`. `loadLive()` раз в 4 с (во время работы) или в 15 с опрашивает `studio_live`. Заполняет `#win-topic`, `#ai-phase`, `#ai-bar`, `#ai-steps` (4 шага STEPS по подстроке фазы), `#stat-*`, `#ticker` (3 строки журнала), пины глобуса (`geoOf`) и полосу `#strip` «Только что отобрано».
- `studio_live` (`internal/web/h_content.go`, `studioLive`) = `parserStatus` (running, phase, activity — последние 8 строк, progress) + до 30 постов пула + `pool`, `topic`.
- Журнал парсера: `p.lines` в `internal/posta/runtime.go` (до `parserLogLines = 400`), после перезапуска сервера читается из `parser-v3.log`. `App.ParserActivity(uid)` отдаёт строки.
- Ход сборщика: `u.ParserProgress(jx.M{...})` в `run_collector` (`internal/posta/parser.go`). Сейчас там total/done/analyzed/added. Счётчики воронки (собрано, кандидаты, отсеянные по причинам `skipped[...]`, отсев быстрой оценкой `pc.stats["rejected"]`, повторы `pc.stats["duplicates"]`) есть только в `u.Log` — в API не попадают.
- Фазы: `parserPhaseWithTopic("сбор постов" | "быстрая оценка" | "полный анализ", topic)`. Автоподбор источников пишет свои фазы.
- Посты пула: `pool_items.data` с полем `timestamp` (когда попал в пул). Оценённые посты уходят в `history_items` (collection liked/disliked/undecided/complaints), `data.timestamp` сохраняется — **проверь это на dev-данных**. Публикации — таблица `published` (`at` bigint, unix).

   - **pointer lock с курсором, который переходит на противоположный край** (`.fakecur`, координаты по модулю `innerWidth/innerHeight`). Владелец просил это отдельно — не выкидывай. На тач-устройствах обычное перетаскивание;

## Часть B — данные города (коммит 2)

1. Новое действие `studio_city` (GET) рядом с `studio_live` в `internal/web/h_content.go`. Ответ:
   ```json
   {"start": "2025-11-02", "days": 364, "pool": [0,3,…], "published": [0,0,…], "topic": "…"}
   ```
   `start` — воскресенье 52 недели назад (как в макете: `today - 52*7 - weekday`), длина массивов = число дней до сегодня включительно. Дни считай в часовом поясе сервера.
2. `pool[i]` — сколько постов попало в пул в этот день по **текущей теме**: `pool_items` + `history_items` по `data->>'timestamp'`, группировка по дню. Пользователь — текущий. Проверь на dev-данных, что у `history_items` timestamp — это время попадания в пул, а не время оценки. Если это не так, бери поле, которое действительно означает «попал в пул», и напиши об этом в отчёте.
3. `published[i]` — `published.at` по дням, у текущего пользователя, по всем каналам.
4. Тест на SQL/группировку с фиксированными датами (граница суток, пустые дни, текущий день).
5. Кэш не нужен: запрос дешёвый. Студия запрашивает `studio_city` при загрузке и после завершения прохода сборщика (`running` сменился с true на false).
6. Переключатель «пул / опубликовано» стоит в строке над тепловой картой, по умолчанию «пул». Над картой: «N в пул за год» (или «N опубликовано за год») и «🔥 K дн.» — серия ненулевых дней до сегодня. При наведении на клетку или дом текст слева заменяется на «30 октября, чт — 5 постов».

## Часть C — журнал и конвейер (коммит 3)

1. **Шаг у каждой строки журнала.** В `runtime.go`, где пишется `p.lines`, параллельно храни шаг, который был текущим в момент записи (`p.lineStages`, той же длины, обрезается вместе с `p.lines`). Ключи шагов: `collect` (сбор постов, площадки, Двач, поиск), `filter` (очередь кандидатов и отсев), `prescreen` (быстрая оценка), `analysis` (полный анализ), `pool` (добавлено в пул, итог), `discovery` (автоподбор источников). Ключ бери из текущей фазы (`ParserPhase`). Чтобы не гадать по тексту, передавай ключ явно: добавь `u.ParserStage(key)` рядом с каждым `parserPhaseWithTopic`. Строкам из файла после перезапуска ставь `""`.
2. `studio_live` отдаёт последние **40** строк журнала (не 8) как `activity: [{"t": "текст", "s": "stage"}]`. Старый формат `activity: []string` нужен вкладкам приложения (`core.js`) — его не ломай. Для студии сделай отдельное поле `activity_stages` или отдельный параметр, как удобнее, только так, чтобы `index.html` продолжил работать.
3. **Журнал в окне** — `.journal` из макета:
   - простой моноширинный текст 11px **без фона**, короткое затемнение только сверху (`mask-image … #000 14%`);
   - **ничего не мигает и не анимируется**: никакого курсора, никакого появления строк. Владелец: «пусть консоль не мигает, она заебала». При каждом опросе **не перерисовывай журнал целиком** — добавляй только новые строки (по перекрытию с прошлой порцией, как `console_.parserLines` в `core.js`), лишние сверху удаляй;
   - время `HH:MM` серым, ✓ зелёным, ✗ красным. Рамки ASCII-боксов вычищай (`cleanLog` уже есть). Строку «⏳ Прогресс…» показывай обычной строкой;
   - пустой журнал вне работы: одна серая строка «Сборщик отдыхает. Последний проход — HH:MM».
4. **Счётчики воронки в API.** В `run_collector` положи в `ParserProgress` объект `funnel`:
   `collected` (собрано постов), `candidates` (кандидатов к проверке), `filtered` (сумма `skipped[...]`), `filtered_by` (карта причин из `skipped`), `prescreen_rejected` (`pc.stats["rejected"]`), `duplicates` (`pc.stats["duplicates"]`), `analyzed`, `added`. Обновляй по ходу прохода там же, где сейчас `analyzed`/`added`. `ParserProgressPublic` должен пропускать `funnel` в ответ.
5. **Конвейер в правой панели** — блок «Конвейер» из макета: название текущего шага, процент, полоса прогресса, под ними вертикальный список шагов. Шаги и числа:
   | Шаг | Число справа |
   |---|---|
   | Сбор | `collected` |
   | Фильтры | `candidates` (отсеяно `filtered`) |
   | ПК-фильтр | отсеяно `filtered_by.ukraine` |
   | Быстрая оценка | прошло `candidates − prescreen_rejected − duplicates` |
   | Анализ моделью | `analyzed` |
   | В пул | `added` |

   **«ПК-фильтр» — так владелец велел называть украинский фильтр в интерфейсе.** Слово «украинский» на главной не пиши. Как он работает (`UASourceBlocked`, язык и происхождение), не меняй.
   Статус шага (✓ / крутится / пусто) определяется по текущему stage. Процент — `progress.share`, как сейчас.
   Вне работы: все шаги с числами последнего прохода (сохраняй последний `funnel` в kv пользователя при завершении прохода), заголовок «Последний проход · HH:MM».
   **Клик по шагу фильтрует журнал:** остаются только строки этого шага, над журналом появляется плашка «только «Анализ моделью» ✕». Повторный клик или ✕ снимает фильтр. Шаги «Фильтры» и «ПК-фильтр» оба показывают строки `filter`.
