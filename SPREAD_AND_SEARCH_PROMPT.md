# Задача: по одному посту с источника, много источников, настоящий поиск по запросу

Ты работаешь в Go-проекте `/var/www/html/posta` (Posta), ветка `go-rewrite`. PHP в проекте больше нет. Владелец жалуется:

1. **Посты из одного источника идут слишком часто.** Нужно правило: с каждого источника — только один пост.
2. **Источников должно быть много.** Раз с источника берётся один пост, ширина воронки важнее её глубины.
3. **Нужен полноценный поиск контента по запросу.** Сейчас «уточнение» в основном фильтрует посты уже известных источников. Владелец хочет: ввёл запрос → система ищет посты про это по площадкам.

Работа делится на две части. **Часть A делай первой и коммить отдельно**, часть B — после неё.

Перед началом:
- посмотри `git status` и `git diff`: в рабочей копии есть чужие незакоммиченные правки (`internal/posta/app_init.go`, `internal/web/h_content.go`, `js/post-*.js`, `js/viewer.js`). Не откатывай их и не включай в свои коммиты;
- номера строк ниже могли сдвинуться — ищи по именам функций.

## Правила проекта (обязательно)

- **Сборка и перезапуск:** `go build -o bin/posta ./cmd/posta && sudo systemctl restart posta`. Правки HTML/CSS/JS работают сразу.
- **Живую БД не трогай.** Тесты — на dev-сервере: `POSTA_DEV=1`, другой порт (8097), dev Postgres на порту 55432. В dev-режиме парсеры не стартуют сами; вход для headless — `/dev-login?sid=…&to=…`.
- **Модели:** вызовы — через `u.LLM.Generate` с нужной ролью (`llm.RoleSmart` и т. п.), как в соседнем коде. Не меняй модель полного анализа на более слабую ради скорости. Платные модели по умолчанию выключены — новые вызовы должны работать на бесплатных и локальных.
- **Никаких `confirm`/`alert`** в JS: вопросы — через `ask()` из `js/core.js`.
- **Настройки поведения** — новые строки `Tunables` в `internal/posta/tunables.go`. Они сами появляются в админке → «Управление». Не плоди констант там, где владелец захочет крутить значение.
- **Украинский фильтр** (`UAItemBlocked`/`UASourceBlocked`) должен работать и для новых путей.
- Пиши как соседний код: короткие русские комментарии над функциями, `jx.M`, `u.Log(...)` на русском.

## Как сейчас (прочитано 2026-10-29, перепроверять не нужно)

### Путь поста

Функция `RunCollector()` (`internal/posta/parser.go`, ~1755):

1. `collectPostsByPlatform(key)` (~363) собирает **все** посты. Источники:
   - каталог темы — до `TelegramPostsPerChannel = 40` постов с канала;
   - Двач и 4chan;
   - находки автоподбора, если у темы мало источников;
   - `PostSearchCollect` — встроенные поиски площадок, тунабл `post_search`.
2. `buildCandidateQueue` (~809) отсекает уже виденное, старое и отфильтрованное, затем сортирует. Внутри вызывается `hotShortlist` (~1082):
   - на один источник там уже стоит ограничение `HotPerSource = 3` (config);
   - хвост очереди перемешивается функцией `InterleaveBySource`;
   - **но с одного источника в очередь всё равно попадают десятки постов**, а после ограничения 3 — ещё и весь хвост.
3. Быстрая оценка (`prescreenBatch`) → полный анализ (`analyzeCandidate`, ~1640) → `admit` → `AddItemToPoolSafely` (~756).
4. **`AddItemToPoolSafely` не проверяет источник.** Если канал хороший, в пул темы (`pool_target` = 50) за один проход легко попадает 5–10 его постов.
5. `PoolOrder` (`content.go`, ~110) только **разносит** такие посты в ленте (окно `PoolDiversityWindow = 6`). Лента всё равно идёт «канал A, B, A, C, A…».

Ключ источника — `ContentSourceKey(item)` (`content.go`, ~166):
- `source_key` (Telegram/VK/RSS/YouTube/TikTok из каталога и поиска);
- для Двача — `dvach:<доска>`;
- иначе — `source:<имя>`.

### Уточнение и поиск сейчас

- **Уточнение** — `settings.query`. Ключ темы становится `«тема ? запрос»` (`SearchTopicKey`, `store.go`). Сохраняет его `save_query` (`internal/web/h_content.go`), поле в интерфейсе — `#query-input` (`index.html`, `js/content.js` → `initializeQueryField`).
- **Что делает уточнение:**
  - посты, где есть запрос (`QueryTextHit`), поднимаются в начало очереди;
  - `RunQueryDiscovery` (`discovery.go`, ~265) ищет каналы Telegram по названию, но только пока у уточнения меньше `TopicQueryMinSources = 3` своих источников, и не больше `TopicQueryDiscoveryPerDay` раз в сутки;
  - `PostSearchCollect` (`post_search.go`) делает **3 запроса за проход**, на всё 60 с. Запросы ротируются из уточнения, хэштегов и запросов профиля темы. Площадки: YouTube (yt-dlp), Telegram (`channels.searchPosts` через аккаунт владельца, **5 поисков в час**, по словам часто платно — хэштеги бесплатно, берётся ≤5 каналов) и VK (`newsfeed.search`, нужен вход в VK). Функция `PostSearchTikTok` написана, но **не вызывается**;
  - после поиска стоит фильтр `PostSearchMatches` (основа слова темы или уточнения в тексте) и фильтр рекламы `PostSearchIsAd`.
- **Итог:** при уточнении большая часть кандидатов — всё те же 40 постов с каждого канала каталога. Поиск — небольшая добавка.

## Часть A. Один пост с источника

**Правило:** в пуле темы (по ключу `SearchTopicKey`) одновременно лежит **не больше одной** неоценённой записи с одного `ContentSourceKey`. Источник, чей пост недавно показали или оценили, отдыхает.

1. **Тунаблы** (группа «Сборщик»):
   - `per_source_pool` (int, по умолчанию **1**, 1–10) — «Записей одного источника в ленте темы»;
   - `source_cooldown_hours` (int, по умолчанию **24**, 0–168) — «Отдых источника после оценки, ч». Пока он идёт, новые посты источника в эту тему не берутся.
2. **`AddItemToPoolSafely`.** Внутри `PoolUpdate` посчитай записи той же темы с тем же `ContentSourceKey`. Если их уже `per_source_pool` — не добавляй и верни `false`. Проверка должна быть внутри замыкания (атомарно), а не до него.
3. **Отдых источника.** Время последней оценки источника в теме храни так, чтобы проверка шла одним запросом, а не обходом всей истории. Например, kv `source_rest:<uid>:<тема>` с картой `source_key → at` и `expires_at` или поле в записи истории — посмотри, что удобнее в `store.go`/`kv.go`. Обновляй значение в `ApplyVote` (`pool_view.go`, ~98) при любом голосе, в том числе «не по теме».
4. **Очередь.** В `buildCandidateQueue`/`hotShortlist`:
   - **до** быстрой оценки уже выброси источники, у которых есть запись в пуле или идёт отдых. Счётчик отброшенных — `skipped["source_busy"]`, выведи его строкой в лог «📌 Тема…»;
   - на один источник в очереди держи не больше **2** кандидатов: лучший и запасной на случай, если лучший отсеется. Константа `QueuePerSource = 2` в `config/consts.go`. `HotPerSource` при этом становится лишним — убери его и всё, что на него завязано.
5. **В цикле анализа** (`RunCollector`, `outer:`): если пост источника принят, удали из ещё не разобранной очереди остальные посты этого источника (оба списка — `candidates` и `queue`), чтобы не тратить на них полный анализ. Самое простое — множество `takenSrc` и `continue` перед `analyzeCandidate` и перед `prescreenBatch`.
6. **Пул, собранный до правки.** Одноразово, при первом проходе — функция по образцу `prunePoolAlreadyRated`: оставь у каждого источника в теме **самую свежую** запись, остальные убери. Медиа освобождай через `MediaReleaseRemoved`. В лог: «Пул: убрано лишних записей одного источника: N».
7. **Двач и 4chan.** Источник — доска. Правило «одна запись» действует и для них.
8. **Проверка (dev):** собери пул на dev-копии с каналом, у которого много подходящих постов.
   - в пуле темы у каждого `ContentSourceKey` ≤ 1 записи;
   - после голоса за запись канала в следующем проходе посты этого канала идут в `source_busy`;
   - лог проходит без паник.

Закоммить: «Сборщик: по одному посту с источника, отдых источника после оценки».

## Часть B. Много источников и настоящий поиск по запросу

### B1. Больше источников за проход

Раз с канала берётся один пост, проходу нужно **много разных** источников. Каналов каталога темы недостаточно.

1. **Тунабл `min_sources`.** Найди его в `tunables.go` и подними значение по умолчанию до **40**. Если `RunSourceDiscovery` от этого начинает блокировать проход слишком надолго, ограничь его по времени, а сам порог не снижай.
2. **Находки автоподбора.** В `collectPostsByPlatform` они подмешиваются только при `TopicLacksSources`. Сделай подмешивание **всегда**, но с одним постом-кандидатом (лучшим по `PostHeat`) с каждой находки. Предел — тунабл `suggestion_sources_per_run` (по умолчанию **30**).
3. **Авторы, найденные поиском.** `PostSearchSuggest` уже кладёт автора принятого поста в отложенные автоподбора — это оставь. Поиск должен давать **по одному посту на автора** (см. B2): каждый найденный автор — новый источник.

### B2. Поиск по запросу — отдельный сборщик

Сделай новый файл `internal/posta/query_search.go`. Когда у пользователя задан запрос (`CurrentQuery() != ""`), `RunCollector` собирает кандидатов **из поиска**, а не из каталога.

**Режим и поле в интерфейсе:**
- Переименуй «Уточнение» в «**Поиск**».
- Плейсхолдер: «что найти: событие, персонаж, бренд, город…».
- Длина — `TopicQueryMaxLen`. Если там меньше 80 символов, подними до 80.
- В логе: `Поиск: «%s» — ищу посты по площадкам (тема «%s» — только для оценки).`
- Ключ пула остаётся `«тема ? запрос»` — так оценки и кэш уже работают.

**Шаг 1. Расширение запроса** (функция `QuerySearchPlan(query, topic)`):
- одним вызовом модели (`llm.RoleSmart`, JSON-схема, temperature 0) получи:
  - `ru` — 3–5 русских формулировок: синонимы и разговорные варианты;
  - `en` — 1–2 английские (для YouTube, 4chan и Reddit-подобных);
  - `hashtags` — 3–5 хэштегов без пробелов;
  - `must` — 1–3 обязательных слова или имени: без них пост точно не про запрос;
- кэш — `CacheSet` на 7 дней по `sha1(query|topic)`;
- если модель недоступна, план собирается из самого запроса: `ru=[query]`, `hashtags=["#"+query без пробелов]`, `must` = самое длинное слово запроса.

**Шаг 2. Опрос площадок** — параллельно, у каждой своя горутина с таймаутом. Общий бюджет — тунабл `query_search_seconds` (по умолчанию **120**). Каждая функция возвращает `[]jx.M` в том же формате, что посты каталога: `source_key`, `source_url`, `found_by`, `posted_at`, `text`, `image`/`video`, `url`, `engagement`. Переиспользуй существующие функции:

| Площадка | Как |
|---|---|
| Telegram, посты | `PostSearchTelegram` на все `hashtags` (бесплатно) и на `ru[0]` (если поиск по словам бесплатный). Лимит `tgSearchPerHour` сделай тунаблом `tg_post_search_per_hour` (по умолчанию 5, не выше 20: можно получить FloodWait). Внутри `PostSearchTelegram` подними `tgSearchChannelPages` 5 → **15** |

Каналы **не** добавляй в каталог — только посты; автор попадёт в автоподбор через `PostSearchSuggest`, если пост примут |
| VK | `PostSearchVK` на `ru[0]` и `ru[1]` (если VK подключён) |
| YouTube | `PostSearchYouTube` на `ru[0]` и `en[0]` |
| TikTok | `PostSearchTikTok` на `hashtags[0]` (сейчас не вызывается — подключи) |

Пост без картинки допустим, только если формат темы разрешает текст (`TopicFormatOf`) |

| 4chan / Двач | Каталоги досок темы (`FourchanBoardsForTopic`, `DvachBoardsForTopic`) — **только из кэша этого прохода или один свежий запрос**. Треды, где в ОП есть слово из `en`/`must`, → 2–3 медиапоста из треда. Без тем-досок — пропуск |
| Pikabu | Только если проверка разметки (см. таблицу) удалась. Иначе — строка в отчёте: «Pikabu пропущен: …» |

Каждую площадку оберни в `recover` и логируй строкой: `Поиск «q»: Telegram 34 (каналов 12), VK 0 (не подключён), YouTube 18, Новости 41, vc/dtf 6, 4chan 3, каталог 9.`

**Шаг 3. Отбор до моделей** (функция `QuerySearchRank`, без LLM):
1. Отсев рекламы — `PostSearchIsAd`, украинского — `UAItemBlocked`, уже виденного — `candidateIsKnown`, старого — `content_max_age`.
2. **Релевантность по словам** `lex`:
   - 1.0 — все слова из `must` есть в тексте или заголовке;
   - 0.6 — есть часть слов `must` или любая формулировка из `ru`/`en`;
   - иначе 0 → отбросить.
   - Сравнивай по основе слова, как в `PostSearchMatches` (обрезка окончания), чтобы «тюменский» находил «Тюмень».
3. **Дубли:** одинаковый текст (`CandidateTextKey`) или одна картинка — оставь более раннюю публикацию (первоисточник).
4. **Один кандидат на источник** — правило части A: лучший по `lex × горячесть` (`PostHeat`, относительная — `hotRelativeHeat`).
5. Сортировка: `lex` ↓, затем горячесть ↓, затем свежесть ↓. Не больше **25%** очереди с одной площадки — как `HotPlatformShare`, переиспользуй.
6. Предел очереди — 200.

**Шаг 4. Модели** — существующий конвейер без изменений:
- `hotTextJudge` для текстовых тем, быстрая оценка, `analyzeCandidate`;
- в промпт анализа добавь строку о запросе — найди, где `AnalysisContextBlock`/`AnalyzeContentWithVision` собирает промпт: «Пользователь ищет: «<запрос>». Пост не про это — relevance ниже 40, даже если подходит теме». Без запроса промпт не меняется.

**Встраивание в `RunCollector`:**
- при запросе вместо `collectPostsByPlatform(key)` → `QuerySearchCollect(key)` (шаги 1–3); дальше всё как было;
- `RunQueryDiscovery` больше не нужен как отдельный шаг: каналы, найденные поиском, приходят постами, а их авторы — через `PostSearchSuggest`. Вызов из `RunCollector` убери, функцию оставь, если её зовёт что-то ещё (проверь `grep`).

**Повторные проходы по одному запросу** не должны находить то же самое:
- кэш выдачи площадок — 1 час (`postSearchCacheTTL`), это оставь;
- храни `query_search:offset:<key>` и при следующем проходе бери следующие формулировки из `ru`/`hashtags` (по кругу, как `DiscoveryRotate`).

Закоммить: «Поиск по запросу: расширение запроса, опрос площадок, один пост на источник».

## Чего не делать

- Не скрапь DuckDuckGo, обычный Bing, Reddit, tgstat — они блокируют сервер.
- Не добавляй найденные поиском каналы в каталог автоматически: только через существующий автоподбор (`DiscoveryDefer`).
- Не снижай порог полного анализа, чтобы «было больше контента».
- Не меняй ключи тем и формат `SearchTopicKey`.
