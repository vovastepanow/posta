# Задача: «Подбор» по свежести без пачек с одного источника + бережный опрос сайтов

Ты работаешь в PHP-проекте `/var/www/html/posta`. Владелец: «пусть источники показываются по порядку свежести постов,
а не пачками с одного сайта. Можно парсить сайты реже и по чуть-чуть, меньше их раздражая».

Две части, A и B, по порядку. После каждой — проверка.

## Общие правила

- **Не делай git commit.** Перед записью в базу: `cp data/posta.sqlite data/posta.sqlite.bak-freshorder`.
- Не открывай приложение в headless-браузере (свежая загрузка = новый пользователь + парсер, который не остановить).
- Не запускай парсер, пока работает парсер пользователя (`pgrep -af parser`).
- Стиль как в окружающем коде: короткие русские `/** … */`, константы в `config.php` с комментарием и единицами.
- `php -l` на каждый изменённый файл, существующие тесты парсера и пула (`ls tools/test_*`) — зелёные.

## Что выяснено (2026-10-24, перепроверять не нужно)

- **Порядок «Подбора».** `add_item_to_pool_safely` (`lib/parser.php:365`) после каждой вставки сортирует пул по
  `card_score` (`lib/quality.php:102`): релевантность + бонус за просмотры + **доля лайков источника** (±15). У постов
  одного источника одинаковая прибавка, поэтому они встают подряд. Карточка «Подбора» — `pool[0]` после
  `pool_for_current_topic` (`handlers/content.php:80`); есть и прямые чтения `pool[0]` (`handlers/content.php` ~694,
  `get_current_item`) — найди все места, где порядок пула важен.
- **Порядок анализа.** `build_candidate_queue` (`lib/parser.php:406`) сортирует кандидатов так: «доверенный» тред →
  холодные каналы в конец → **доля прошедших у канала** → горячесть → свежесть. В итоге сначала разбирается **весь**
  лучший канал, и в пул за проход заходит пачка из одного места. За проход добавляется до `CONTENT_ADDED_PER_RUN = 30`,
  кандидатов — до 500, остальные отбрасываются (и при следующем проходе собираются заново).
- **Опрос сайтов.** `collect_posts_by_platform` (`lib/parser.php:181`) на **каждом** проходе заново скачивает **все**
  источники каталога темы: `collect_catalog_source` (`lib/parser.php:54`) → страница t.me (`fetch_telegram_channel_page`,
  уже есть `host_throttle('t.me', 1.5)`), RSS, ОК, TikTok (yt-dlp), VK; плюс доски Двача (`dvach_boards_this_run`) и 4chan
  (у 4chan уже условные запросы с 304 — `fourchan_get_json`). Проходы идут один за другим, пока пул темы не наполнится до
  `CONTENT_POOL_TARGET = 50`.
- У записи каталога есть `activity` (`source_activity`, `lib/sources.php:530`): `last_post`, `per_week`, `checked_at`;
  обновляется после каждого сбора (`apply_source_activity`) и сохраняется пачкой `save_catalog_entry_updates`.
- **Внимание к данным:** в 02:13 другая сессия сделала `data/posta.sqlite.bak-wipe` и очистила базу: в каталоге сейчас
  только 23 RSS-ленты, Telegram-каналов и досок Двача нет (владелец в курсе). Код пиши для всех площадок, а проверяй на
  том, что есть. Для проверки можно собрать временную копию базы из `bak-wipe` во временном файле —
  **рабочую базу из бэкапа не восстанавливай**.

## Часть A. Показ по свежести, без пачек

1. Функция `pool_order(array $pool): array` в `lib/content.php` (или рядом с пулом):
   - сначала по свежести поста: `posted_at` по убыванию (нет — `pooled_at`);
   - потом **разнообразие**: жадно, сверху вниз; если следующий пост того же источника (`content_source_key`), что и
     предыдущий, взять ближайший более старый из **другого** источника в пределах окна `POOL_DIVERSITY_WINDOW = 6`.
     Нет такого в окне — оставить как есть (порядок по свежести важнее);
   - записи разных тем не смешивать: порядок внутри темы, как сейчас фильтрует `pool_item_in_topic`.
2. `add_item_to_pool_safely`: вместо `usort(... card_score ...)` — `pool_order`. `card_score` остаётся для **допуска и
   вытеснения** (что держать в пуле), но не для порядка показа. Напиши это в комментарии.
3. Порядок должен быть одинаковым везде, где показывается пул: «Подбор», «Предложка» (если она берёт из пула), счётчики.
   Пройди по `pool_load()` / `pool_for_current_topic()` и при чтении для показа вызывай `pool_order`, чтобы и старые
   пулы, сохранённые в прежнем порядке, сразу шли по-новому.
4. Анализ по кругу (`build_candidate_queue`): после нынешней сортировки разложи кандидатов по источникам, сохранив
   порядок источников (по доле прошедших) и порядок внутри источника, и **бери по одному с каждого по кругу**. В пул за
   проход будет попадать по одному-два поста с каждого источника, а не 30 из одного.

**Проверка A.** Тест `tools/test_fresh_order.php` (стиль `$check(...)` как в `tools/test_news_4chan.php`):
- пул из 3 источников по 4 поста с разным временем: порядок по свежести и нет двух одного источника подряд, если в
  окне есть другой;
- один источник — порядок просто по свежести;
- `build_candidate_queue` на подставных постах: первые N кандидатов — из N разных источников.

## Часть B. Реже и по чуть-чуть: у каждого источника свой интервал

1. **Интервал опроса** источника — по его активности:
   `interval = clamp(средний промежуток между постами / 2, SOURCE_POLL_MIN, SOURCE_POLL_MAX)`, где промежуток =
   `7 сут / activity.per_week`. Константы: `SOURCE_POLL_MIN = 20 мин`, `SOURCE_POLL_MAX = 6 ч`. Нет `activity` — источник
   «просрочен» (опросить). Пример: 100 постов в неделю → ~50 мин; 10 в неделю → 6 ч; 500 в неделю → 20 мин.
2. **Кэш постов источника**: после успешного сбора сохраняй посты источника в `kv` (`source_posts:<хэш platform|id>` =
   `{at, posts}`; храни только поля, нужные кандидату, не HTML). Источник, которому ещё рано, на проходе **не идёт в сеть**:
   его посты берутся из кэша. Уже разобранные отсеет `candidate_is_known` / `$seen`, как сейчас; так не пропадают
   посты, до которых проход не дошёл.
3. **Бюджет на проход**: в сеть — не больше `SOURCE_FETCHES_PER_PASS = 10` источников, самые просроченные первыми
   (`(now − checked_at) / interval` по убыванию). Остальные — из кэша, их очередь на следующих проходах.
4. Двач и 4chan: для досок — тот же подход проще: каталог доски не чаще раза в `BOARD_POLL_MIN = 10 мин` (кэш ответа
   каталога и тредов в `kv`). У 4chan уже есть 304-кэш — проверь, что его хватает, и не дублируй.
5. Исключения:
   - **ручное обновление** (кнопка поиска контента / «Подобрать», найди, что ставит `refresh_content`) и **новая тема**
     (у темы нет кэша) — опрашивают всё, что просрочено, но в пределах бюджета 10;
   - `host_throttle` оставить как есть;
   - заморожённые источники — как сейчас (`is_source_frozen`).
6. Журнал: одна строка за проход — «Опрошено N из M источников, остальные из кэша (следующий через ~X мин)».
   Строки «Парсинг … @канал…» — только для реально опрошенных.

**Проверка B.**
- Тест (в `tools/test_fresh_order.php` или отдельном) с подставной отправкой (`$GLOBALS['telegram_page_fetch_stub']`
  уже используется в `tools/test_preview_pages.php` — посмотри, как): 15 источников, бюджет 10 — в сеть пошли 10 самых
  просроченных; повторный проход сразу — 0 в сеть, посты из кэша; источник с `per_week = 500` снова просрочен через
  20 минут (подставь `checked_at` в прошлое), с `per_week = 10` — нет.
- Интервалы считаются правильно на краях (`per_week = 0`, нет `activity`, очень большой `per_week`).
